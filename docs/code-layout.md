## Server

The server lives in `src/`:

- `src/server.ts`: the entry point.
  Builds the page, loads the access token, builds the `Dashboard`, starts the HTTP and WebSocket server on its routes and socket handlers, then starts it.
  `PORT` sets the port, 4317 by default.
  On `SIGINT`, `SIGTERM`, or the desktop shell's pipe ending, `shutdown()` awaits `Dashboard.stop` before it stops the server and exits; the process's `exit` handler calls `Dashboard.exited`, which writes what the stores have not and releases the owner lock, however the process exits.
  `restart()`, which **Update dashboard** calls, stops the same way, keeps the owner lock for the same pid and port, and runs the server's own command again in the same process through `process.execve`; a signal or the pipe ending during a restart makes it exit instead.
  Every dashboard socket first hears the page's build, `pageBuild` in `src/server/page.ts`, so a page another build served reloads.
- `src/preflight.ts`: the first import of `src/server.ts`.
  It checks the Bun version and loads `src/omp/install.ts`, so a missing requirement, such as `omp` absent from `PATH`, prints one `omp-agents:` line saying how to fix it and exits 1 instead of a stack trace.
- `src/server/dashboard.ts`: `Dashboard`, the composition root: it builds the stores, `LiveSessions`, `Views`, `Notices`, `ListRegistry`, `Broadcasts`, the inboxes, `Worktrees`, the starter, `RoutineRunner`, `ProjectRunner`, `MergeCleanup`, `MergeQueue`, `Loops`, and the socket handler in dependency order, each handed the parts above it, and owns the live-update switch, the registry listing, the file rescans, the activity check, the merge queue's 15-second loop, and the owner lock's takeover.
  Two edges point down, closing the only cycles: a live session's update reaches the parts built after `LiveSessions`, and a notice change reaches the `Broadcasts` that reads the notices; no constructor calls either.
  It also owns the `ForeignUsage` index that each Analytics read refreshes.
  Nothing follows the registry, watches a directory, or publishes before `start(server)`; `stop()` first stops the loops and both inboxes, so no tick publishes while the rest shuts down, then ends the sessions started here, hangs up on the shells, stops omp-stats, flushes the stores, and aborts the routine commands still running.
- `src/server/list-registry.ts`: `ListRegistry`, the authoritative builders for the nine whole-list socket messages, registered beside their store apply functions in `Dashboard`.
  An edit publishes its list when it changes; a no-op resends the current list only to its requesting peer.
  Routines and scheduled sends register only edits: their run-now and send-now actions stay with their runners, and notices and the queued merges keep their own action handlers.
- `src/server/broadcasts.ts`: `Broadcasts`, what every socket hears on the `roster` topic: the roster, the past list, plan usage, and the whole lists from `ListRegistry`.
  Opening sockets get every registered list; `pushList` publishes only a message that changed, while roster and past messages keep their row-level deltas.
- `src/server/http.ts`: the request checks (`Host`, `Origin`, `Sec-Fetch-Site`, the token cookie), `refuseUntil`, which holds the dashboard socket back until the sessions are reattached, and the JSON answer helpers.
  `/api/` requests and sockets are admitted by the cookie alone, so a stray `?token=` on a signed-in request changes nothing; only `/` reads `?token=`, to set the cookie.
  `src/server/auth.ts` keeps the token file and parses the cookie, `src/server/address.ts` names the port, host, and listening line that the desktop shell shares, and `src/server/page.ts` bundles `web/index.html` in memory and serves it only to a signed-in browser.
- `src/server/routes.ts`: the `/api/` endpoints, in nine groups (sessions, integrations, providers, calendar, Gmail, pull requests, files, todos, and the dashboard's own update), each handed only its part of `RouteEnv`.
  Every read goes through `get`, and every write through `write(parse, run, refuse?)`, which checks the origin and the JSON body, answers a body `parse` refuses with its response, and maps an error `run` throws through `refuse`, else to a 500.
  `src/server/wire.ts` parses every socket message and request body into typed values; every parser returns a `Parsed<T>` from `src/json.ts`, `{ ok }` or `null`, and the two OAuth client parsers `{ error }` in place of `null`, a reason the page shows.
  A shape the server also keeps in a file is parsed by its domain module, which `wire.ts` imports, so a file store never imports the transport: `parseRoutineSpec` in `src/routines.ts`, `parseScheduledSpec` in `src/shared/scheduled.ts`, `parseEventWhen` in `src/shared/calendar.ts`, and `parseNewSessionRequest`, the new-session start that a scheduled start keeps, in `src/shared/sessions.ts`.
- `src/terminals.ts`: the terminal panel's shells, each in a pseudo-terminal with its scrollback; `src/server/terminal-socket.ts` handles the `/ws/terminal` sockets that attach to them, and `src/shared/terminals.ts` holds the shapes and messages the page shares.
- `src/server/socket.ts`: handles each socket message, answering through a `Peer` from `src/server/request-ledger.ts`; see [Socket requests](architecture.md#socket-requests).
  `src/server/start.ts` starts, forks, resumes, and replays dashboard sessions for the page's `start` and `resume-all` requests, and refuses to fork or resume a Claude Code or Codex session before it starts omp.
  `src/server/session-end.ts` ends a session for the page's `end` message and for the end inbox: `endSession` stops it, then calls `Worktrees.removeCheckout` on its worktree from `SessionFacts`, else its cwd, and logs the blockers of a checkout that stays, which **Settings → Worktrees** still lists.
  `src/server/discussions.ts` holds `Discussions`, the **Ask about this** answers under way by the socket that asked, which `discuss` starts, `discuss-stop` aborts, and a socket's close aborts all of; see [Ask about this](architecture.md#ask-about-this).
- `src/server/live-sessions.ts`: the one registry of running sessions, terminal and dashboard alike, each behind the `LiveSession` interface in `src/live-session.ts`.
  Each session's `row()` returns a `LiveRow`, what its transport knows; `rows()` adds `cwdDisplay`, the session's `unread` turn, the session's facts, and the subject a quick action started it on, to make the roster rows.
  The registry keeps each session's unread turn, the turn it ended since a page showed it in a focused window: `Dashboard` sets it with `markUnread` at `turn-ended` and clears it with `markRead` at `turn-started`, both from `turnUpdate` in `src/live-session.ts`, and `markRead` clears it for the page's `read` message too; see [Session notifications](architecture.md#session-notifications).
  The registry indexes its sessions by session id for `bySessionId`, and rebuilds the index when a session joins or leaves or a dashboard session reports `switched`.
  `add` refuses a session whose `finished()` already holds, such as a dashboard session whose omp exited as it spawned, and `start.ts` answers that start with an error.
  After each registry poll, `follow` hands every session the listed hosts and removes the ones that report `finished(now)`; a terminal guest decides there when to rejoin, so the registry reads no result from `follow`.
- `src/server/loops.ts`: the registry, rescan, usage, routine minute, notice, activity, and pull loops, each started through `repeat`, which waits for a tick to finish before it schedules the next and logs a tick that throws, so no loop overlaps itself or dies on one failure.
  It keeps one recursive watcher per session format's root: it makes omp's when missing, and watches Claude Code's and Codex's only once they exist, trying a missing one again on each rescan.
  `Loops.stop` stops every loop, closes the watchers, and drops a pending re-read; a file change reported after it is ignored.
- `src/server/session-files.ts`: the session files on disk, omp's, Claude Code's, and Codex's, re-read file by file as the watchers report them, and the past list, each row with its `source`.
  It asks each format in `src/session-formats.ts` whether a changed path is its session file, and lists and reads through the format that owns the file.
  `src/server/interrupted.ts` keeps which dashboard sessions were interrupted, once `recover` learned which of those that ran when the last server stopped survived it.
  `src/server/views.ts` points each open view at its file and keeps its tail and media tree together for their shared lifecycle: a view nobody shows any more, or one whose file changes, has its tail and media tree closed, so a read still in flight and the tail's held-back updates publish nothing.
  It applies a session's starting prompt to that session's main view with each of its live events, so a live user message and the removal of the prompt it replaces go out together.
- `src/shared/`: every type that crosses the socket or the HTTP API, one file per domain.
  Each answer a polled store keeps in localStorage has its decoder beside its type: `decodePullRequestList`, `decodeTicketsAnswer`, `decodeIntegrationsAnswer`, `decodeAnalytics`, `decodeGoogleStatus`, `decodeCalendarEventsAnswer`, `decodeLocalEventsAnswer`, and `decodeInboxAnswer`, which check every field of the type.
  `protocol.ts` holds `ServerMsg` and `ClientMsg`; `sessions.ts` the roster and past rows (`RosterHost`, `PastSession`), views, user requests, and starts; `transcript.ts` the transcript items, changed files, and images; `github.ts` the pull request and pull request list shapes; `tickets.ts` the Linear issues; `accounts.ts` the MCP integrations and their OAuth client setups; `calendar.ts` the Google calendars, their events, a new event, and the events kept on this computer; `git.ts` the checkouts and branches; `models.ts` the models, routing, plan usage, and omp's files; `notices.ts` the bell's notices; and `analytics.ts` the Analytics section.
  `accounts.ts` also holds `AccountId`, `GoogleAccount`, the `accounts` column of `MCP_SERVICES`, and `visibleAccounts`, the Google accounts a workspace shows: those linked to it and those linked to none.
  `transcript.ts` also holds `isDashboardPrompt`, which tells a prompt the dashboard sent in the user's place, such as a project's update, which the page hides.
  Every place that shows a prompt's text checks it: the transcript and its starting prompt in `src/transcript.ts`, the **Trajectory** in `src/trajectory.ts`, the queued rows and ↑ in `web/components/composer-queue.tsx`, the live title's `/rename` in `src/dashboard-session.ts`, and the past title in `src/omp/sessions.ts`; a new place that shows prompt text needs the same check.
  `transcript.ts` also holds `MEDIA_FILE_TYPES` and `mediaUrl`, the `GET /api/media` address of an image or video on this computer, which the media tree and the page both build.
  `mcp-servers.ts` holds the rows and bodies of Settings › MCP servers, and `mcp-catalog.ts` the catalog of remote servers it offers.
  `mcp-status.ts` holds `McpRemoteStatus` and `McpTool`, where omp stands with a remote MCP server, which an integration's `McpConnection` in `accounts.ts` and a server's `McpServerStatus` in `mcp-servers.ts` both build on.
  `gmail.ts` holds `MailThread` and `InboxAnswer`, the Inbox page's conversations, and `ThreadAnswer` with its `MailMessage`, `MailPerson`, `MailBody`, and `MailAttachment`, one conversation in full.
  `newSessionRequest` in `sessions.ts` builds a new-session start with every option not given defaulted, for the socket's parser, the routine runner, and their tests.
  `SessionFacts` in `sessions.ts` declares a session's pull requests, Linear issues, /ship stage, worktree, and branch once, and `RosterHost` and `PastSession` extend it.
  `parseNewSessionRequest` there checks one, with `parseImages`, `parseModel`, `parseThinking`, and `parseSkill`, for the socket's `start` and a start kept in `scheduled.json`; `parsePullRequest` in `github.ts` checks a pull request's owner, repository, and number.
  The routine shapes (`Routine`, `RoutineRun`, `RoutineChange`) live in `src/routines.ts`, which the socket messages import.
  `selectorOf` names a model as `provider/id`, which both session transports and the model picker use, and `pullRequestUrl` a pull request's GitHub page, which the server's prompts and the page's links share.
  `prompt-files.ts` holds the files a prompt carries as text: `withFiles` and `splitFiles`, which put them after the typed text and take them back off, `plainText`, which tells a text file, and the limits and body of `PUT /api/attachment/document`.
  `slug.ts` holds `slug`, the lower-case, dashed name segment that a worker's branch and a project's inbox file take.
  `discussions.ts` holds **Ask about this**'s request, its events, the limits `parseDiscussionRequest` in `src/server/wire.ts` holds it to, `discussionPrompt`, the one message the model gets, and `sessionMessage`, what **Send to session** sends.
- `src/omp/`: the facades over omp's modules: `modules.ts` loads them, `install.ts` finds the package and its CLI and reads its `package.json` with `readManifest`, and `collab.ts`, `rpc.ts`, `sessions.ts`, `stats.ts`, `config.ts`, `discovery.ts`, `mcp.ts`, `models.ts`, `model-updates.ts`, `release.ts`, `prompts.ts`, `documents.ts`, and `isolation.ts` wrap one area each.
  `context-index.ts` keeps the context-source index beside omp-stats' database: each request of each session file split by source, re-read only for files that changed.
  `discussion.ts` holds `answerDiscussion`, one streamed model call on omp's `smol` role, else `default`, that answers **Ask about this** outside every session.
- `src/analytics.ts`: merges Claude Code's and Codex's requests into omp-stats' `StatsRead` with `withForeignUsage`, then folds per-file rows into sessions and workspaces.
  It joins each saved session's `SessionSummary`, its title and working directory, without reading transcripts.
- `src/context-sources.ts`: splits a request's input by source, from its context messages and a subagent's recorded system prompt, and folds the index's rows into the Analytics tab's context-source report.
- `src/proc.ts` runs subprocesses with the environment as this process holds it then, and `runShell` a routine's shell command, `src/json.ts` narrows untyped JSON (`isObject`, `isNonEmpty`, `isSafeInteger`, `isDay`, `str`, `oneOf`, `isTexts`, `errorText`), `src/fs.ts` replaces a file through a temporary one beside it and holds `JsonFile`, the load/save store behind `interrupted.json`, `todos.json`, `routines.json`, `scheduled.json`, `workspaces.json`, `pins.json`, `calendars.json`, `google-accounts.json`, `events.json`, `projects.json`, `review-drafts.json`, `notices.json`, and `settings-sync.json`.
  `childEnv` in `src/proc.ts` is that environment without the server's own `PORT` and `OMP_AGENTS_PARENT`, which the omp sessions, the terminal panel's shells, and routine commands get, so a server an agent starts neither takes the dashboard's port nor exits when its stdin ends.
  A `JsonFile`'s `save` writes once per event-loop turn however many changes arrive in it, and `flushJsonFiles` writes them at once as the server stops or exits.
  `ReducerFile` wraps `JsonFile` for the lists the server changes through a reducer, `todos.json`, `routines.json`, `scheduled.json`, `workspaces.json`, `pins.json`, `calendars.json`, `google-accounts.json`, `events.json`, `projects.json`, and `review-drafts.json`: it loads the value or an empty one, applies a change through its `reduce`, saves only when the change gives a new value, and, for a `shared` file another server also writes, reads the file again before each change.
  `src/json.ts` also holds `Parsed<T>`, the `{ ok }` or refusal every parser returns, and `BASE64`, which the socket's parsers and the domain parsers share.
  `src/paths.ts` names these files beside the access token, the old `google.json` the server deletes, and, under the data directory, each project's notes (`projectNotesDir`), the user's (`userNotesDir`), and the settings sync's repository (`settingsSyncRepo`).
  `src/json.ts` also composes guards of whole shapes (`fields`, `tagged`, `arrayOf`, `nullable`), which `decoder` turns into decoders.
- `src/dashboard-session.ts`: drives one session that the dashboard started, over RPC, including serialized model changes and state refreshes; `reattach` opens one a previous server started, and `dispose` hangs up without stopping omp.
  `src/keeper.ts` is the session keeper, the detached process that holds one session's omp, lends its stdio frame by frame to one server at a time over a Unix socket, so the session outlives the server, and stops every process omp started when the session ends; `src/keeper-link.ts` is the server's side, which starts, lists, and connects to keepers, and `reattachAll` in `src/server/start.ts` attaches to them at startup.
  `src/keeper-wire.ts` holds the greeting, the stop line, the pid file's name, and `KeeperMeta`, the only words the two sides share, so the keeper's bundle holds none of the server; `src/process-census.ts` is the keeper's `ProcessCensus`, which notes the processes under omp with `ps` and stops the noted ones when the session ends, and `stopTree`, with which the server stops a stuck keeper's tree.
  `src/prompt-turn.ts` holds its `PromptTurn`: whether the main agent's turn runs and which prompt omp admitted while idle has not shown yet, with one method per event that moves them.
- `src/guest.ts`: runs one Collab guest per terminal session.
  `src/subagents.ts` parses the host's subagent registry and its lifecycle and progress frames (`parseAgents`, `parseSubagentFrame`) for both transports, finds each subagent's transcript file, and lists every subagent transcript under a transcript's artifacts directory (`artifactsDir`, `subagentFiles`).
- `src/serial-lane.ts`: `SerialLane`, which runs work one call at a time in arrival order; both transports order a session's prompts, aborts, and flushes with it, and the routine runner serializes ticks and run-now claims.
- `src/user-requests.ts`: parses the RPC and Collab question frames into one request shape, writes the answers back, and keeps each session's pending questions.
- `src/commands.ts`: the composer's `/` and `@` completions, and the expansion of file commands and skills before a guest prompt.
- `src/tail.ts`: reads one transcript file incrementally, decodes each line through its format's `decode` from `src/session-formats.ts`, and feeds each entry to both folds below.
  `src/line-reader.ts` holds `FoldedFile`, which keeps a fold of a file's lines up to date, applying only appended complete lines and starting a fresh fold when the file shrinks.
  `src/tail.ts`, `src/media.ts`, `src/changes.ts`, `src/session-facts.ts`, and `src/foreign/usage.ts` each fold transcripts through it.

  The inbox takes `add`, and `set-status` `done`, deletes each file it applies, and moves any other to `<name>.invalid` with a logged reason, so the server stays the only writer of `todos.json` and an agent cannot undo what you did.
  The extension's `before_agent_start` handler reads `todos.json` at each prompt and adds to the system prompt the title and id of the open top-level todo that links to its session, and of each other open one whose `addedBy` is its session, so the agent checks them off once done.
  `add` returns the open todo its session already added with the same title instead of adding it again.
- `src/server/end-inbox.ts`: ends the sessions that omp's `end_session` tool (`templates/omp/agent/extensions/end-session.ts`) asks to end, one `<session id>.json` each in `end-inbox/` beside `todos.json`.
  The tool writes its request at `agent_end`, after the turn that called it, and deletes it at the next `agent_start` or `session_shutdown`, so a request names a session that idles.
  The inbox drains when the directory changes and after each registry poll, finds the live session through `LiveSessions.bySessionId`, ends it through `endSession`, the path **End session** takes, so the session is not marked interrupted and its worktree goes too, then deletes the request.
  A request is `{ v: 1, sessionId }`; `END_REQUEST_VERSION` is the version this server reads, a request without `v` reads as version 1, and one of any other version moves to `<name>.invalid`, so a later change to the request's shape has a version to key on.
  A request whose session this server does not host yet stays for a later drain, and so does one for a session started in a terminal while another server owns the lock, since every server follows those; a file that is not a request, or whose name is not its session id, moves to `<name>.invalid`.

## Starter kit and docs

`templates/omp/` holds the omp starter kit and its installer, `templates/omp/install.ts` (`bun run omp-template`).
Its `agent/` files are the default kit.
`templates/omp/README.md` lists what each of its extensions does.
`agent/extensions/google-accounts.ts` tells a session which Google account each Gmail and Google Calendar MCP server signs in as, and which addresses its workspace links; `templates/omp/google-accounts.test.ts` tests its workspace lookup against a real repository and a linked worktree outside it, and its prompt text, and `templates/omp/extensions.test.ts` runs its hook on scratch files.
`agent/extensions/request-log.ts` both records each provider request and, run with Bun, rebuilds the requests a session file records and checks their hashes; `templates/omp/request-log.test.ts` records requests through omp's own blob store and checks every rebuilt body against the one sent.
`agent/extensions/ship.ts` gates draft PRs and putting a PR live on bash commands it splits into words outside quotes; `templates/omp/ship.test.ts` tests that parsing, the `gh pr view` selector it builds from a `gh pr ready`, and the owner check that skips the gate for someone else's repository.
`maintainer/` is the maintainer git profile, `AGENTS.md` and `templates/omp/maintainer/docs/git-workflow.md`, copied only when you pass `--maintainer`, and a file there replaces the `agent/` file with the same path.
[Template sync](../CODING_STANDARDS.md#template-sync) says how to copy an edited live file back.
The default `agent/AGENTS.md` keeps worktree and force-push safety inline and links to the model and review references under `agent/docs/`.
The profile's `templates/omp/maintainer/docs/git-workflow.md` detects Graphite with `git rev-parse --path-format=absolute --git-common-dir`, so the same procedure works from a checkout, a linked worktree, or a nested directory.
The repository's agent guide links to the [coding standards](../CODING_STANDARDS.md), which every contributor follows, and to [agent smoke checks](agent-smoke.md) for server authentication and lifecycle, browser verification, and desktop verification.
It also links [decisions](decisions.md), why each design choice was made, [`LEARNINGS.md`](../LEARNINGS.md), pitfalls agents hit here, and [`GLOSSARY.md`](../GLOSSARY.md), the project's vocabulary.
[Getting started](getting-started.md) walks a new user through a first session and each integration's sign-in, and `docs/images/` holds the README's screenshot.
`patches/omp-18.12.3-paid-cursor-fallback.patch` preserves the external OMP runtime's paid Cursor fallback implementation and regression tests against upstream `v18.12.3`.
It is not loaded or applied by the dashboard; [omp modules](architecture.md#omp-modules) describes its base, application, and installation boundary.
`scripts/omp-release.ts` (`bun run omp-release [version]`) checks an omp release against this codebase: it installs that release and the tested one, runs `src/omp/modules.ts` and `bun test` against the release, and writes a report of the test result, the omp files that changed between the two, and their changelogs to `node_modules/.cache/`.

## Desktop

`desktop/` holds the desktop shell; see [Desktop shell](architecture.md#desktop-shell).
`desktop/main.ts` is its main process, with `desktop/shell-env.ts` and `desktop/updates.ts` for the packaged app, and `bun run desktop` at the root installs the package and starts it from the checkout through `desktop/launch.ts`; `scripts/build-desktop-artifact.ts` packages it (see [Packaging and releases](architecture.md#packaging-and-releases)).
`desktop/preload.ts` is the window's preload, which gives the page the `DesktopBridge`, and `desktop/attention.ts` takes what the page sends through it: the Dock badge's count and the session notifications, whose click shows the window on the session.
On macOS the launcher clones `node_modules/electron/dist/Electron.app` to `desktop/dist/omp agents.app`, sets its `CFBundleName`, `CFBundleDisplayName`, and `CFBundleIdentifier`, gives it an `.icns` that it renders from `icon.png` with `sips` and `iconutil`, signs it ad hoc, and runs that copy, because the Dock, the menu bar, and Cmd+Tab read an app's name and icon from its bundle.
It rebuilds the copy when Electron's version or `icon.png` changes.
`desktop/icon.svg` is the app icon, the logo mark on a macOS-style tile, and `desktop/icon.png` is that SVG rendered at 1024 px, because Electron reads no SVG; render it again after you change the SVG.
The page's favicon, `web/favicon.svg`, is the bare mark.
