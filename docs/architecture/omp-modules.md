# omp modules

The server imports omp's own modules from the installed package, so it does not reimplement a protocol, the encryption, or the session-file format, and it always speaks the same version as the sessions it shows.
`src/omp/modules.ts` loads every module once and checks at startup that each export this app uses exists, naming the omp version and the missing export when one does not.
It casts each module to an interface in `src/omp/module-types/`, the subset of omp this app reads, one file per area: Collab, session files, RPC, config, models, discovery, MCP, stats, and processes.
Those files hold only types, so the app imports a type from them directly and every value from `modules.ts`, whose import runs every check.
It finds the package through `omp` on `PATH`, or `OMP_PACKAGE_DIR` when set; with a Bun global install that is `~/.bun/install/global/node_modules/@oh-my-pi/pi-coding-agent`.
`bun run omp-release` checks a new omp release against these modules and the files listed below; the [omp release skill](../../.agents/skills/omp-release/SKILL.md) says how to read its report.

Four runtime patches change omp itself, each kept in `patches/` with its regression tests against upstream tag `v18.18.0`, commit `b5a6b2f7e5b6606b6562e678ead83f21738f34a0`; do not apply them to another release without porting and verifying them.
The dashboard applies none of them, so installing or upgrading stock omp removes them all.
From a clean checkout of that release, apply all four, run their tests, and build the CLI:

```sh
for p in paid-cursor-fallback runtime-tool-contracts cursor-dynamic-tools-rule credit-balance-fallback; do git apply /absolute/path/to/omp-agents/patches/omp-18.18.0-$p.patch; done
bun install --frozen-lockfile
bun --cwd=packages/ai test test/auth-storage-model-usage-health.test.ts test/cursor-usage.test.ts test/cursor-system-prompt-history.test.ts test/rate-limit-utils.test.ts test/anthropic-stream-envelope.test.ts
bun --cwd=packages/coding-agent test test/paid-cursor-routing.test.ts test/write-xdev-dispatch.test.ts test/task/seance.test.ts test/agent-session-tool-rebuild-skip.test.ts test/tools/read-repeat-hint.test.ts test/agent-session-retry-fallback.test.ts
bun --cwd=packages/coding-agent run gen:bundle
```

A source checkout needs the matching pi-natives addon in `packages/natives/native/` before those tests.
Build once with all four applied, since a CLI built without one of them drops it.
Install the rebuilt `dist/cli.js`, then copy each source file the patches change, as `git diff --name-only v18.18.0 -- packages/ai/src packages/coding-agent/src` lists them, over the installed one in `pi-ai/src/` or `pi-coding-agent/src/`, keeping a rollback copy of everything replaced.
Already-running sessions keep their loaded code until restarted.

- `omp-18.18.0-paid-cursor-fallback.patch` adds the opt-in `retry.paidFallback` setting, which the [routing policy](../../templates/omp/agent/docs/model-routing.md) describes with its billing limits.
- `omp-18.18.0-runtime-tool-contracts.patch` lists MCP devices by name per server in `read xd://` and mount notices, in `pi-coding-agent/src/internal-urls/router.ts`, `pi-coding-agent/src/internal-urls/xd-protocol.ts`, and `pi-coding-agent/src/tools/xdev.ts`.
  The read router applies ordinary line and raw selectors to `xd://` documentation; device writes reject those suffixes instead of executing the bare device.
  Missing-device errors give a short discovery hint rather than dumping the mounted inventory.
  Historical task consults, in `pi-coding-agent/src/task/seance.ts` with guidance in `pi-coding-agent/src/prompts/tools/seance-task-guidance.md`, search session IDs only in the caller's artifacts and current project, including when given a full UUID.
  Cross-project callers pass the exact `file` returned by eval's archive as `sourceSession`; the Memory curator's saved job follows that handoff.
- `omp-18.18.0-cursor-dynamic-tools-rule.patch` adds `cursorDynamicToolsRule` to `pi-ai/src/providers/cursor.ts`: a system-prompt entry naming the tools Cursor hides behind `GetDynamicTools`, all but its native ones; the dashboard's own [Cursor paragraph](front-end-components.md#session-visuals) still reaches its sessions without it.
- `omp-18.18.0-credit-balance-fallback.patch` adds Anthropic's 400 `credit balance is too low` to `CREDITS_EXHAUSTED_PATTERN` in `pi-ai/src/error/rate-limit.ts`, so a spent API key is a usage limit that moves the session to the next fallback entry and keeps the key skipped until its backoff ends; [its record](../decisions/2026-11-07-a-spent-api-key-is-a-usage-limit-in-a-runtime-patch.md) says why.

Paths in this document that start with `pi-coding-agent/`, `pi-ai/`, `pi-catalog/`, `pi-tui/`, `pi-utils/`, or `omp-stats/` are inside that install, in `@oh-my-pi/`.
They are not in this repository.
The main ones:

- Collab: `pi-coding-agent/src/collab/registry.ts`, `protocol.ts`, `crypto.ts`, and `relay-client.ts`.
  `collab/settings.ts` exports `cfgCollabAutoStart`, whose native default complements `Settings.getGlobalSettings` when Get started reads `off`/`view`/`control` without a workspace's overrides.
- Session files: `pi-coding-agent/src/session/session-listing.ts` and `session-loader.ts`.
  `appendCustomMessageEntry` in `pi-coding-agent/src/session/session-manager.ts` gives a `custom_message` entry the timestamp of the message it records, which `#persistMessageEnd` in `agent-session.ts` passes.
  `SessionManager.renameSessionTitle(path, title, { cwd })` there is how `renameSessionFile` in `src/omp/sessions.ts` retitles a saved session, as omp's session picker does: it claims omp's lease on the session (`claimSession` in `session-storage.ts`) before it loads the file and holds it until the title is written, and answers `null` without writing when another process holds the lease, the file moved, or the title is blank once control characters read as spaces.
  It sets the title through `setSessionName(title, "user")`, which writes the header's title slot in place and appends a `title_change` entry, and a `"user"` title outranks every later `"auto"` one.
  The lease lives in `~/.omp/run/session-owners`, except that omp gives a `bun test` process a directory of its own and names it in the environment.
  `listSessionsReadOnly` caches each file's header by modification time and size, so a renamed file reads with its new title.
  `findSessionContinuation` there returns the copy `omp --resume` opens when a session went on in a sibling file whose header names it in `continuationOf`, which `continuationOf` in `src/omp/sessions.ts` reads for a resume, since RPC `switch_session` opens only the file it is given, and for the past list, which leaves out a session it names a copy for.
  `SessionInfo.continuationOf` carries that header field into the listing.
  Worktree protection and private purges use `visitEntriesFromFileStream` through `readSessionHeader` instead: it reads only the first native record, capped at 1 MiB as omp's header reader is, without trusting a listing cache after a replacement that preserved size and modification time.
- Interrupted turns: `pi-coding-agent/src/session/exit-diagnostics.ts` (`createInterruptedTurnAbortMessage`), which `endsMidTurn` in `src/omp/sessions.ts` uses to refuse forking a session that ended mid-turn.
  It checks the branch from the leaf that `resolveSessionLeafId` in `pi-coding-agent/src/session/session-entries.ts` returns, as omp's load does, since a late `model_usage` entry is written last but points back at the leaf with `activeLeafId`.
- Images: `pi-coding-agent/src/session/blob-store.ts`, which moves a prompt's image out of the session file into `blob:sha256:<hash>`, and `getBlobsDir` in `pi-utils/src/dirs.ts`; `src/transcript.ts` and the `/api/image` route read them.
- Provider requests: `emitBeforeProviderRequest` in `pi-coding-agent/src/extensibility/extensions/runner.ts` hands each provider's request body to the extensions in load order, with the request's model as `ctx.model`, and `templates/omp/agent/extensions/cache-tail.ts` edits it.
  The providers call it through `onPayload`; `pi-ai/src/providers/anthropic.ts` still edits the body after the hook to withhold kill-switched fields and to fit server-side compaction, Bedrock, and Vertex, and compaction, branch summaries, and titles never reach the hook.
- Bot and personal extensions: `ExtensionAPI` and `ToolDefinition` in `pi-coding-agent/src/extensibility/extensions/types.ts`, whose `registerFlag`, `getFlag`, `on("session_start")`, `on("before_agent_start")`, `registerTool` with `loadMode` and `approval`, and `typebox` the `ExtensionApi` in `src/omp/extension-kit.ts` copies by hand, which the Bot, shepherd, designer, and personal extensions share; see [Bots](bots.md) and [Personal sessions](personal-sessions.md).
  `ExtensionRuntime` in `loader.ts` keeps a flag's value in `flagValues`, and `pi-coding-agent/src/main.ts` sets it from the command line through `applyExtensionFlags` in `pi-coding-agent/src/cli/extension-flags.ts` only after every extension has loaded, so the extension reads its flags when a turn starts.
  `typebox` is omptype's TypeBox shim, `Type` in `omptype/src/typebox.ts` (`@oh-my-pi/omptype/typebox`), not `@sinclair/typebox`; its `Object`, `String`, `Integer`, `Boolean`, `Literal`, `Union`, `Array`, and `Optional` build the routine tools' parameters, and `pi-agent-core/src/tool-arguments.ts` validates each call against them through pi-ai's `validateToolArguments` before the tool runs.
- Documents: `convertBufferWithMarkit` in `pi-coding-agent/src/utils/markit.ts`, the converter behind omp's `read` of a PDF, Word, PowerPoint, Excel, or EPUB file, which `src/omp/documents.ts` calls for `PUT /api/attachment/document`.
- RPC: `pi-coding-agent/src/modes/rpc/rpc-client.ts`, `rpc-frame.ts`, and the frame types in `rpc-types.ts`.
  `RpcClient` drops `extension_ui_request` and `session_info_update` frames, so `src/omp/rpc.ts` reads them from its own copy of omp's stdout (`UNROUTED_FRAMES`); see [Dashboard sessions](dashboard-sessions.md).
  `src/omp/module-types/rpc-host-tool.ts` holds the host tool a session serves over RPC, which `src/omp/rpc.ts` registers, so that module does not import the client declaration that names its `RpcClient`.
  `RpcClient`'s `spawn` option may return any process with `pid`, `exited`, `stdin`, `stdout`, `peekStderr`, and `kill` (`RpcAgentProcess`); `start()` waits for omp's `ready` line, sends `negotiate_protocol` when it offers protocol 2, then `set_host_tools`, and a stdout that ends makes it call `kill`; see [Session keepers](dashboard-sessions.md#session-keepers).
  omp answers `negotiate_protocol` again whenever it is sent (`rpc-mode.ts`), and `RpcFrameDecoder` throws on a chunk sequence that does not start at index 0 or that another frame interrupts; omp writes a frame over 1 MB as such a sequence.
  `get_state` reports `isStreaming` and `isCompacting`, and `get_subagents` returns `RpcSubagentSnapshot`s with the fields of a subagent lifecycle frame.
  `agent_end` carries `isTerminal: false` when more of the run follows, such as a queued follow-up, a retry, or a background job's result, and adds `awaitingAsyncWork: true` when only a background job's result can resume it (`AgentSession` `#settleAgentEnd` in `session/agent-session.ts`); `yielded: true` does not single that case out, since omp keeps it on a terminal end it re-tags non-terminal for a queued follow-up (`#flushPendingAgentEnd`).
  omp's eval kernels and subagents spawn with Bun's `detached`, as session leaders of their own (`pi-coding-agent/src/eval/kernel-base.ts`, `task/executor.ts`), and its background jobs lead process groups of their own, so only a walk of the process tree finds them, and only while omp runs.
  `get_available_models` returns omp's whole `Model` objects, with `name`, `contextWindow`, `api`, `identity`, and `serviceTiers`; `get_state` adds `fastModeEnabled` and `fastModeActive`, and `setFastMode` sends `set_fast_mode`.
  `get_state` also exposes `autoCompactionEnabled` and `goal`; `RpcClient.setAutoCompaction` and `RpcClient.goal` drive their short controls.
  Goal events carry `goal_updated`; completion clears native mode state, so the dashboard retains the completed event until cleared.
  `goals/state.ts` defines `GoalModeState` and `GoalRuntimeEvent` around pi-tui's `Goal`; `parseRpcGoal` validates the subset the dashboard reads before retaining a completion event.
  `goal.continuationModes` in `goals/settings.ts` defaults to interactive continuation only.
  `advisor/settings.ts` supplies the configured default and `advisor/config.ts` discovers the WATCHDOG roster; RPC still has no field for the session's actual advisor enabled state.
  `session/model-compaction-threshold.ts` applies per-model overrides before `pi-agent-core/src/compaction/compaction.ts` resolves the trigger token count, so the ring does not duplicate threshold math.
  `RpcClient.prompt` resolves with the request id once omp admitted the prompt, and `onPromptResult` delivers that prompt's `prompt_result` (`rpc-prompt-results.ts`); see [Dashboard sessions](dashboard-sessions.md).
  `RpcClient` has no method for `set_session_name` (`rpc-mode.ts`), which sets a `"user"` title and emits no event, so `rename` in `src/dashboard-session.ts` writes the frame and then reads `get_state`.
  Host tools: `RpcClient`'s `customTools` option (`RpcClientCustomTool`), which `start()` sends as `set_host_tools`, so a new process for the same session gets them again, and `setCustomTools`, which replaces them for a session the server attached to; `pi-coding-agent/src/modes/rpc/host-tools.ts` runs them as strict tools, sending `host_tool_call` and waiting on `host_tool_result` or its own `host_tool_cancel`, and `defaultLoadModeForToolName` in `pi-coding-agent/src/tools/essential-tools.ts` makes one without `loadMode: "essential"` only discoverable.
  A host tool stays registered through `newSession`, `switchSession`, and `/move` in one process, since omp builds `SessionTools` once per `AgentSession` (`pi-coding-agent/src/session/session-tools.ts`).
  Extensions: `omp -e <file>` (`pi-coding-agent/src/main.ts`, `additionalExtensionPaths`) loads in `rpc-ui` mode too; `pi-coding-agent/src/discovery/omp-extension-roots.ts` dedupes by path only, so the same extension at two paths loads twice.
- Service tiers: `serviceTierFamily` and `shouldSendServiceTier` in `pi-ai/src/types.ts`, which `fastAvailable` in `src/omp/models.ts` calls to decide, as `setFastMode` in `pi-coding-agent/src/session/model-controls.ts` does, whether `/fast` can turn on for the live model.
- Settings and discovery: `pi-coding-agent/src/config/settings.ts`, `pi-coding-agent/src/discovery/index.ts`, and `pi-coding-agent/src/task/discovery.ts`.
  Skill frontmatter: `SkillFrontmatter` in `pi-coding-agent/src/capability/skill.ts` keeps any key of a user's skill, but `validateAgentSkillFrontmatter` in `pi-coding-agent/src/discovery/agent-plugin-format.ts` refuses a plugin's or a skillshare pack's skill with a top-level key outside its list or a non-string `metadata` value, so `src/omp/workflows.ts` reads the `workflow` tag from `metadata.tags`.
  `src/omp/discovery.ts` keeps a `Skill`'s `name` and `frontmatter` and a `SlashCommand`'s `name` (`pi-coding-agent/src/capability/slash-command.ts`) from the capability items, so the workflows read neither file themselves.
  `config/registry.ts`'s `all` supplies known setting IDs for the installer-owned readiness plan.
  Settings › omp settings reads omp's settings panel through `src/omp/agent-settings.ts`: `orderedSettings` from `config/all-settings.ts`, the panel's entries before it groups them, and `SETTING_TABS`, `TAB_METADATA`, `getSettingsForTab`, and `numericOption` from `pi-tui/src/overlays/settings-defs.ts`, which turn them into tabs, groups, and controls.
  It reads each row's handle from `config/registry.ts`: its type, default, `ui`, `isCredential`, `envName`, and `provenance`, with `getGlobalSettings` and `getProjectSettings` from `config/settings.ts` for the user's and the workspace's values, and writes one with the handle's `set` or `unset`.
  `createSettingsHost` in `config/settings-ui.ts` is not used, since it reads omp's global `settings` instance, not one loaded for a workspace.

  Settings › omp memory reads omp's memory through `src/omp/memory.ts`; its settings are rows of omp settings.
  `resolveMemoryBackend` from `memory-backend/index.ts` gives the backend a session resolves, whose `buildDeveloperInstructions` gives the block a new session gets, and whose `clear` and `enqueue` clear Local and Sharpshooter and rebuild Local's summary, which need no session.
  Local's store is `getMemoryRoot` from `memories/index.ts`; Sharpshooter's is `sharpshooterBankDir` from `sharpshooter/paths.ts` with the files `SHARPSHOOTER_MEMORY_FILES` in `sharpshooter/types.ts` names, and `sharpshooterQueueDepth` from `sharpshooter/queue.ts`.
  Mnemopi's banks come from `loadMnemopiConfig` in `mnemopi/config.ts` and `getMnemopiScopedBanks` and `getMnemopiScopedDbPaths` in `mnemopi/state.ts`, which need `loadMnemopiCore` first; the page opens each bank with the `Mnemopi` class `loadMnemopi` gives, as `createMemory` there does, and redacts new text with `redactMemorySecrets` from `memory-backend/redact.ts`.
  `MnemopiSessionState.editScopedMemory` and `mnemopiBackend.clear` are not used, since both need a running session, so the page mirrors their rules; `bankRows` lists a bank's working and episodic rows from `beam.exportToDict` with the visibility rules omp's `get` applies (`pi-mnemopi/src/core/beam/store.ts`), and its facts from the `facts` table through `beam.db`, since omp lists no facts.
  Hindsight's bank is `computeBankScope` from `hindsight/bank.ts` over `loadHindsightConfig` from `hindsight/config.ts`, and its rows `listMemories` on the client `createHindsightClient` in `hindsight/client.ts` makes.
  Project code: `forgetReadFiles` in `src/omp/discovery.ts` calls `reset` from `discovery/index.ts`, which empties the capability file cache (`capability/fs.ts`), and `discoverProjectCode` calls `loadCapability` with `providers`, since the extension loader (`extensibility/extensions/loader.ts`) asks only the native provider, and with `filter`, since the custom tool loader (`extensibility/custom-tools/loader.ts`) imports only `.ts`, `.js`, `.mjs`, and `.cjs` files before omp dedupes by name.
  TypeScript slash commands come from `discoverCustomCommands` in `extensibility/custom-commands/loader.ts`, and project language server configs from `configFileSources` in `utils/config-file-sources.ts`, the stack `loadConfig` in `lsp/config.ts` reads, kept to the files in `cwd` and in the project directories `getConfigDirPaths` in `config.ts` names; see [Project trust](project-trust.md).
- Starter-kit plugins: `pi-coding-agent/src/extensibility/plugins/marketplace/registry.ts` exports `getMarketplacesRegistryPath`, `getInstalledPluginsRegistryPath`, `readMarketplacesRegistry`, and `readInstalledPluginsRegistry`.
  Get started reads these registries and the current project's registry, located by the read-only `resolveOrDefaultProjectRegistryPath` in `discovery/helpers.ts` with native `getProjectDir`.
  It never initializes CLI config, migrates plugin data, or installs anything while checking readiness.
- Extensions library: `pi-coding-agent/src/extensibility/plugins/marketplace/manager.ts` supplies source catalogs and scoped marketplace lifecycle; `registry.ts` supplies its cache and registry paths.
  `pi-coding-agent/src/extensibility/plugins/marketplace/registry.ts` catches parse errors and returns an empty registry, so `assertRegistryReadable` validates its top-level version and collection before passing a mutation to the manager.
  `extensibility/plugins/manager.ts` supplies npm/git/link lifecycle, and `loader.ts`'s `resolvePluginManifestEntries` reads declarations without executing entrypoints.
  `skillshare/client.ts` supplies explicit-registry search, `installer.ts` installs/updates/uninstalls with native script consent callbacks, and `manifest.ts` supplies native IDs, store paths, and scoped manifest locations.
  `discovery/index.ts` supplies provider state, foreign-user-source opt-ins, and read-only settings binding; `src/omp/scoped-discovery.ts` serializes that process-wide binding.
  `src/omp/extensions.ts` keeps installed scope copies separate and discovery preview distinct from session runtime; see [Extensions library](extensions.md).
- Credentials: `pi-coding-agent/src/session/auth-broker-config.ts` (`discoverAuthStorage`) and `pi-ai/src/registry/oauth/index.ts` (`getOAuthProviders`).
  `connectedProviders` in `src/omp/models.ts` keeps the `/login` providers that have a credential, as omp's RPC `get_login_providers` marks them `authenticated`, and any provider whose model config sets an API key, plus API credits when that key is stored.
  It constructs `ModelRegistry` without `refresh`, and a local model found with no key stays out.
  `connectedProviderIds` keeps a sign-in provider with any credential, a catalog provider whose model config sets an API key, and API credits when its key is stored. Another catalog provider's stored key does not count. `configuredProviderIds` is only the config-key set, plus `anthropic-api` when an Anthropic API key is stored, which the footer shows when `omp usage` has no balance for it.
  It opens the credential store on each call and closes it, so a login in a terminal counts at the next call.
  Settings › Providers runs omp's own `/login` and `/logout` through `src/omp/providers.ts`: `AuthStorage.oauth.login` (`pi-ai/src/auth-storage.ts`) with `captureBrowserSession` from `pi-coding-agent/src/utils/browser-session.ts` for a cookie sign-in, `formatLoginIdentity` from `pi-coding-agent/src/cli/oauth-terminal.ts`, `ModelRegistry.refreshProvider` from `pi-coding-agent/src/config/model-registry.ts` afterwards, as `omp login` does, and `toLogoutAccounts` and `logoutCredential` from `pi-coding-agent/src/slash-commands/helpers/logout.ts`.
  Direct Anthropic API-key entry uses `AuthStorage.credentials.upsert` and `removeById` from `pi-ai/src/auth/types.ts`, through the discovered store, including its broker.
  The key is filed under `anthropic-api`, not beside the Anthropic sign-in, and `src/omp/api-credits.ts` adds that provider to `models.yml` with `auth: none` so omp sends the stored key.
  A key saved earlier under `anthropic` is moved once, when the dashboard server starts (`adoptLegacyApiCredits` in `src/omp/providers.ts`), not when a page reads providers.
  The `models.yml` entry is inserted under `providers:` and marked, so removing the last key deletes that block and leaves the rest of the file as it was.
  The saved key has `source: "login"`, so it ranks above an environment variable, as `pool.storeLoginApiKey` does.
  Upsert matches an API key by its value, so a different key is removed after the new one is stored.
  Replacing the provider's whole credential set is not used: a broker snapshot does not hold the real OAuth refresh token.
  `oauth.login` stores a string result under the method id, not under `storeCredentialsAs`, so this entry does not register a second OAuth provider.
- Plan billing: `AuthStorage.usage.reports` in `pi-ai/src/auth-storage.ts`, opened through `discoverAuthStorage` and called by `src/omp/usage.ts`.
  Its options are `{ provider?: string, signal?: AbortSignal }`, and its result is `Promise<UsageReport[] | null>`.
  The narrow contract lives in `src/omp/module-types/models.ts`; every native value still comes through `modules.ts`.
  Native reports retain Claude's raw billing, including non-USD money that normalized limits can omit; the dashboard supplements only the CLI report for the same account.
  This uses omp's credential owner, not direct token or billing requests; see [Plan quota](plan-quota.md).
- Model selectors: `parseRetryFallbackSelector` in `pi-coding-agent/src/session/retry-fallback-chains.ts`, which only `readSelector` in `src/omp/config.ts` calls.
  `readSelector` reads a selector against the `provider/id` of the listed models, so a `:level` splits off only after an id that `omp models` lists, and returns the selector's provider, id, and suffix.
  `resolveSelector` keeps the read only when its model is listed, and `routedSelectors` names every selector of the routing: each role's, and each fallback chain's key and entries.
- Model roles: `pi-coding-agent/src/config/model-resolver.ts` (`expandRoleAlias`, `resolveRoleChain`), whose `@role` aliases `resolveRoles` in `src/omp/models.ts` follows for `GET /api/models/roles`.
  `modelEntries` reads each of the `routedSelectors` with `readSelector` and maps it to a listed model with `resolveProviderModelReference`, which follows retired variant ids such as `grok-4.7-high` and dotted spellings such as `claude-fable-5.1`.
- Dictation: `pi-coding-agent/src/stt/settings.ts`, `stt/models.ts`, and `stt/stt-controller.ts`, omp's speech-to-text settings, models, and recorder, `modes/rpc/rpc-dictation.ts` (`RpcDictationBridge`), and `config/model-roles.ts` with `resolveRoleChain` from `config/model-resolver.ts`, which `src/omp/dictation.ts` uses to read whether dictation is on and to run one capture in the server; `enableDictation` in `src/omp/config.ts` sets the user's `stt.enabled`; see [Dictation](dictation.md).
  It opens the settings and the models you can call with `openRegistry` in `src/omp/models.ts`, over `ModelRegistry`'s `refresh` in `pi-coding-agent/src/config/model-registry.ts`.
- MCP: `pi-coding-agent/src/mcp/json-rpc.ts` (`callMCP`), `config.ts` (`loadAllMCPConfigs`), `client.ts` (`connectToServer`, `listTools`, `disconnectServer`), `oauth-credentials.ts` (`removeManagedMcpOAuthCredentials`), `oauth-discovery.ts` (`discoverOAuthEndpoints`), `oauth-flow.ts` (`MCPOAuthFlow`), and `config-writer.ts` (`addMCPServer`, `updateMCPServer`, `removeMCPServer`, `setMcpServerEnabled`, `validateServerName`, `readMCPConfigFile`), which `src/omp/mcp.ts` wraps for the tickets page, Settings › Integrations, and Settings › MCP servers.
  The MCP sign-ins and sign-outs read and write omp's credential store through the same `discoverAuthStorage`, opened and closed on each call.
  `pi-coding-agent/src/commands/token.ts` uses `refreshStoredManagedMcpOAuthCredential` from `oauth-credentials.ts` to refresh a managed token and persist its rotated refresh token before printing the access token.
- Completions: `pi-tui/src/autocomplete.ts`, and the skills and slash commands in `pi-coding-agent/src/extensibility/`.
- Paths: `pi-utils/src/dirs.ts`, which names omp's sessions directory, and `getWorktreesDir`, its directory of isolation sandboxes.
- Cleanup: `src/omp/gc.ts` uses `omp gc --json` because `runGcCommand` in `pi-coding-agent/src/cli/gc-cli.ts` prints its report rather than returning it.
