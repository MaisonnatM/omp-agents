# Desktop shell

`desktop/` is the desktop app: an Electron main process, `desktop/main.ts`, in its own package, so the root `bun install` never fetches Electron.
Electron's main process runs on Node, which cannot load omp's TypeScript modules or the server's `Bun.*` calls, so the shell runs the server as a child process on Bun and never imports it: `bun src/server.ts` from a checkout, and in the packaged app the Bun binary it ships in `Contents/Resources/server/bin/bun` on the bundled `server.js`, with `OMP_AGENTS_RESOURCES` naming that directory (`src/server/resources.ts`) so the server reads its prebuilt page and the starter kit from it.
omp's sessions run on that same Bun, through `process.execPath`.
It imports only Node-safe helpers from `src/paths.ts`, `src/json.ts`, `src/fs.ts`, `src/server/auth.ts`, `src/server/address.ts`, `src/server/update-journal.ts`, `src/shared/dashboard-update.ts`, `src/shared/git.ts`, `src/shared/desktop-bridge.ts`, and `src/shared/startup.ts`; `bun build` bundles them into `desktop/dist/main.cjs`, and `desktop/preload.ts` into `desktop/dist/preload.cjs`.
Its global quick-capture shortcut dispatches `QUICK_TODO_EVENT`, from `src/server/address.ts`, in the page, which `web/app.tsx` answers by opening the command palette on its **Create todo** view.
`src/server/address.ts` holds what the two processes must agree on: the port from `PORT`, the host names the server answers to, the line it prints once it listens, and the line it prints before it restarts in place.
`OMP_AGENTS_HEADLESS=1` keeps the window hidden and the app out of the Dock, shows no notification, badge, or sound, and a Dock click, a second launch, or the quick-capture shortcut does not show the window; agents' smoke checks drive it over CDP ([Agent smoke checks](../agent-smoke.md#desktop-smoke)).

- At launch it calls `loadToken`, as the server does, so whichever runs first creates the token file, and asks `GET /api/hello?nonce=<nonce>` on the port with a fresh random nonce.
  Only an omp-agents server that holds this token can answer with `helloProof`, the HMAC of the token, the port, and the nonce, so the shell sends the token nowhere else.
  A refused connection starts a server.
  Any other answer means the port is taken, and the window says so.
- The shell takes the server as started once it prints `listeningLine` (`omp-agents (omp v…) on http://127.0.0.1:<port>`), not once the port answers: another server that took the port while this one built its page would answer too, and the shell would then own a server that is about to fail.
- It spawns the server with `OMP_AGENTS_PARENT=stdin` and an open stdin pipe that it never writes to.
  The server calls its `shutdown()` when that pipe ends, which it does however the shell exits, `SIGKILL` included, so no server outlives the app and holds the port.
  On a normal quit, the shell sends `SIGTERM` and waits up to 10 seconds for the server to write its stores and let go of its sessions.
  Quitting leaves the sessions the server started running, as a restart or a crash does: the server cannot tell a quit from a restart, **Restart to Install** quits too, and the next launch shows them live again, while **End session** stays the one way to stop a session.
- **Update dashboard** runs the server again inside the same process ([Updating the dashboard](updating-the-dashboard.md)), so the shell keeps its child, its pipes, and the window; the page in the window reloads itself once its socket hears a new build.
- `desktop/server-supervisor.ts`, free of Electron so a test runs it on Bun, starts the server and follows it; `desktop/main.ts` only turns what it reports into the window's page: the dashboard once a server listens, unless the window shows it already, the error page with the server's last 40 lines and **Retry**, or the missing-omp notice.
  A server that prints no listening line within 60 seconds of its start, or of the `restartingLine` it prints before `process.execve`, is stopped and counts as stopped.
  Each time the server stops while the app is not quitting, the supervisor first reads the checkout's update record: when the stop was an update's new build that was not listening, which a server that restarted in place is not until it prints its listening line again, or an update cut short mid-move, it takes the checkout back to the commit that ran before and starts that at once, as the record's states say.
  A rollback that cannot finish, such as when `git reset --keep` refuses a changed file, shows the error page with git's reason, and its **Retry** tries again.
  Otherwise a server that never listened since the last start or **Retry** shows the error page at once, and `OMP_MISSING_EXIT` (79) the missing-omp notice.
  A server that listened is started again after 1, 2, 5, then 15 seconds, by how many times it stopped within the last 5 minutes (`afterLoss` in `desktop/restart-policy.ts`); the 5th stop within 5 minutes shows the error page with **Retry**, which starts it at once and forgets the stops so far.
  The window keeps its page while the server is away, and the page reconnects by itself.
  Quitting and **Restart to Install** stop the server, a rollback's `bun install`, and a wait before a restart alike, so nothing starts again after them.
  The packaged app runs from no checkout, so it restarts its server but never rolls back.
- The window loads `http://127.0.0.1:<port>/`, a navigation that sends `Sec-Fetch-Site: none`, so `servePage` answers it with the page, and the socket's `Origin` matches its `Host`.
  A custom scheme for the page would fail that check.
- No address carries the token.
  The preload, before the page's scripts run, asks the main process over the synchronous `ACCESS_CHANNEL`, and writes each entry of the answer into the page's `localStorage`.
  The main process answers `pageAccess(token)`, the token and the media key, only when the message comes from the window's own dashboard frame, and `null` otherwise, so the shell's own notice pages get nothing.
- `setWindowOpenHandler` denies every new window: it loads the dashboard's own page, with the address's hash, in the window itself, and hands other `http:` and `https:` addresses, `/api/` media links included, to `openOutside`; `will-navigate` hands any address outside the dashboard's origin to `openOutside` too.
  `openOutside` gives `openOwnApp` the first try and `shell.openExternal` the rest.
  An empty `window.open`, which a page opens before it knows the address, returns `null`, so the MCP sign-ins in `web/use-sign-in.ts` then open the address themselves once the server names it.
- The page runs with context isolation and the sandbox on, and gets no Node or Electron API.
  Its preload, `desktop/preload.ts`, hands it only `window.ompDesktop`, the `DesktopBridge` of `src/shared/desktop-bridge.ts`, whose `badge`, `alert`, and `playSound` send one IPC message each; see [Session notifications](notifications.md#session-notifications).
  Its `onTargetURL`, absent in an app built before it, receives the address of the link under the pointer or keyboard focus from the window's `update-target-url` event, and an empty string when the window blurs or navigates.
  Its `signIn`, which the page calls when it holds no token, asks the shell to load the dashboard again with the page's hash, so the preload writes the current token.
  The main process reloads only when the token file now holds a token other than the one it last handed out, as after a rotation; otherwise a reload would loop, and the page stays on its notice that the server holds another token.
  Its `pickDirectory`, absent in an app built before it, which **Settings › Workspaces** calls for **Choose folder…**, invokes `PICK_DIRECTORY_CHANNEL`, and the main process answers with the folder picked in `dialog.showOpenDialog` over the window, or `null` when it was cancelled.
  The main process takes each one only from the window's own dashboard frame.
  Its optional no-argument `installStarterKit` invokes a fixed installer only from the dashboard's main frame, returning `{ ok, message }` to Get started; the menu uses the same in-process operation with native dialogs, never `--force`.
  Its `openDashboard`, absent in an app built before it, which **Review visuals** calls for each listed page, invokes `OPEN_DASHBOARD_CHANNEL` with the address, and the main process answers whether `openOwnApp` took it, only for the window's own dashboard frame.
- The session's permission handlers grant only clipboard writes and full screen, and only to the dashboard's own page; every other request is refused.
  Session notifications come from the main process, so the page needs no notification permission.
- The app keeps its data, its localStorage, window bounds, and single-instance lock, in `port-<port>` under Electron's `userData`, so a smoke run on another port is an instance of its own beside your app.
- `openOwnApp` opens the page of another omp-agents server on this computer, such as an agent's smoke server, in an instance of its own, since no browser tab or Browser guest gets the token.
  It takes only `http://127.0.0.1:<port>/` or `http://localhost:<port>/` with any hash, on a port other than the app's own, and only once `probe` gets that port's `helloProof` for this token; it then spawns the app, `process.execPath` with the app's directory when unpackaged, with the page's address as its argument.
  An app launched with such an address, by `openOwnApp` or as `bun run desktop http://127.0.0.1:<port>/#…`, takes its port from it ahead of `PORT`, loads the address's hash, and never starts a server: when nothing answers there, its window says so, with **Retry**.
  A second launch on a running instance's port loads the address it was launched with in that instance's window, through `second-instance`, so one smoke server has one window, showing the last page opened.
- A main-frame load of the dashboard that fails (`did-fail-load`), for example after the server the window used stopped, shows the shell's error page with **Retry** instead of Chromium's.
- The page's **Browser** is a `<webview>` of a session's dev server, which `webviewTag` allows ([Browser](../usage/browser.md)).
  `desktop/browser-guests.ts` owns its guests: `will-attach-webview` refuses one that a page other than the dashboard adds, or whose address is not on this computer (`isLoopbackUrl` in `src/shared/desktop-bridge.ts`), and forces its preload, context isolation, the sandbox, no Node, and the `persist:omp-preview` partition, so the app's cookies and storage outlive a launch apart from the dashboard's.
  Each attached guest follows any `http:` or `https:` navigation and redirect in place, so a sign-in round trip through a provider ends in the guest, and refuses other schemes.
  A web address that `appAddress` in `src/shared/desktop-bridge.ts` maps, a loopback port reached from a page off this computer or on one of the session's ports where neither the session nor another server listens, or where another checkout of the session's app does, loads on the session's port last in the guest's history instead; the page reports each guest's `BrowserPorts`, its server menu's candidates and the session's `otherPorts`, with the bridge's `browserPorts` on `BROWSER_PORTS_CHANNEL`, which main takes only from the dashboard.
  A `window.open` with window features, Electron's `new-window` disposition and the shape of a sign-in popup, opens as a child `BrowserWindow` in the same partition and sandbox, with `window.opener` kept so it can hand its result back, and gets the same rules, port mapping included; any other new window, such as a `target="_blank"` link, goes to `openOutside`, and the page sets `allowpopups`, without which the guest drops a new window instead of asking.
  The partition's permission handlers grant only `clipboard-sanitized-write`, for the app's own Copy buttons, and only to a guest of the dashboard.
  The guest's preload, `desktop/preview-preload.ts`, runs `dist/preview-pick.txt`, the IIFE that `bun build` makes of `desktop/preview-pick.ts` and the preload inlines, in the app's own world on `DOMContentLoaded`, as T3 Code runs its picker: react-grab's `getElementContext` reads React's fibers there, which the isolated world cannot see.
  That script puts a `PreviewPicker` on `window.__OMP_PICK__`, which `web/use-webview.ts` calls through the webview's `executeJavaScript`: `select` turns **Select** on with its outlines, drawn in a closed shadow root over the app where react-grab's `getElementBounds` places them, inside a same-origin iframe too, and labeled with the nearest React component's name that bippy reads, and its capture-phase pointer listeners, which keep each press from the app's own handlers; `deselect` and `clear` drop elements; `resolve` hides the hover outline and returns each selected element's `getElementContext` text, or its tag and HTML after 1.5 seconds.
  Each change, and each scroll or resize, posts a `PreviewSelection` under `PREVIEW_SELECTION_CHANNEL`, whether **Select** is on and where the selected elements show, which the preload checks with `isPreviewSelection` in `src/shared/desktop-bridge.ts` and forwards with `sendToHost`; the page checks it again, places the card, and lets **Erase** drop an element from it; a new page in the guest reports none, and the page turns **Select** on again there.
  Any script in the app can post that message or replace the picker, so the app can change what one **Attach** appends to the composer, never send it; `resolveSelection` in `web/use-webview.ts` reads nothing unless the guest's page is on this computer, so a site the app signs in through cannot append either.
  The preload also reports an Escape the app left unhandled on `PREVIEW_ESCAPE_CHANNEL`, since a key pressed in the guest never reaches the page, and the page stops picking or restores a maximized Browser on it.
  While **Select** is on, it hands V, R, D, and E pressed outside a text field to the page on `PREVIEW_PICK_KEY_CHANNEL`, and `usePicking` in `web/components/browser-capture.tsx` switches to the mode whose `browserPick` shortcut in `web/shortcuts.ts` has that key; a test keeps the preload's `PICK_MODE_KEYS` and those shortcuts alike.
  **Screenshot** and **Attach** ask the shell with the bridge's `captureBrowser` on `BROWSER_CAPTURE_CHANNEL`, a handler on the dashboard window's own `webContents.ipc` that answers only the dashboard with `capturePage()` of that guest as PNG bytes, resized to the screen size's CSS width while one is emulated, so the picture is 1×.
  A **Screen size** other than **Fit panel** is emulated by the shell, not the page: the page sends each guest's `BrowserScreen`, the size, its rotation, and whether picking is on, with the bridge's `screenBrowser` on `BROWSER_SCREEN_CHANNEL`, and `emulate` in `desktop/browser-guests.ts` attaches the guest's `debugger` and sends `Emulation.setDeviceMetricsOverride`, touch emulation, and `Emulation.setUserAgentOverride` from `SCREEN_DEVICES` in `src/shared/desktop-bridge.ts`.
  Picking turns off only `setEmitTouchEventsForMouse`, so the mouse picks while the app keeps its layout; **Fit panel** detaches the debugger, which drops every override, and a guest another debugger holds stays as it fits.
  The page names the size only once a guest's first page is ready, so a guest that opens on a size is reloaded with the guest's own `reload()` once the overrides are sent; the protocol's `Page.reload` sent to a guest reloads the dashboard that embeds it.
  The page lays the `<webview>` out at the size's CSS width and height and shrinks it to the Browser with a CSS `transform: scale`, which the guest's hit testing and `capturePage()` both follow, so a zoom change sends the shell nothing; picking draws over the shrunk frame, and `usePicking` keeps each selected element's box in the app's CSS pixels and shows it at the current zoom with `scaleArea` in `web/browser-model.ts`.
  For **Attach**, `annotationFile` in `web/components/browser-capture.tsx` draws the Region boxes and Draw lines on it and crops it to them and to the selected elements, whose outlines the app drew, and the page attaches it through `attachToComposer`.
  Only once the picture is attached does the page append the annotation chip, `annotationReference` in `web/prompt-tokens.ts` of `annotationText` in `web/browser-model.ts`, through `appendToComposer`, and stop picking, so a failed capture or a closed conversation keeps the marks.
- The packaged app, launched by Finder or at login, gets no shell environment, so `desktop/shell-env.ts` runs the login shell (`$SHELL -ilc`) once at startup and merges its environment into `process.env` before the server starts; omp, `gh`, and `git` are then found as in a terminal.
  In the packaged app, Retry repeats discovery for `PATH`, `BUN_INSTALL`, and `OMP_PACKAGE_DIR` alone, from a shell started with launchd's bare environment, so it reads what the rc files set now rather than echoing the app's own values; the initialized home, XDG directories, port, and Electron locations stay unchanged.
  A checkout keeps the environment it was launched with.
  Only `OMP_MISSING_EXIT` (79) shows the server-free missing-omp notice with a fixed copyable install command and Bun guidance; other startup failures retain the ordinary error page and output.
  See [Get started](get-started.md#missing-omp-before-the-server-exists) for this narrow startup contract.
- **Open at Login** is the packaged app's own login item (`setLoginItemSettings`); a checkout has none, and the app removes the LaunchAgents that `bun run desktop` once wrote.
- `desktop/updates.ts` updates the packaged app through electron-updater from GitHub Releases: a check 15 seconds after launch and then every 30 minutes, a download in the background, a notification, and **Restart to Install** in the app menu, which stops the server first; an update left waiting installs when the app quits.
  Squirrel.Mac installs only an update signed by the same Developer ID as the running app, so ad hoc builds check and download but never install.

## Packaging and releases

`scripts/build-desktop-artifact.ts`, modeled on T3 Code's script of the same name, builds `desktop/dist/resources`: the server bundled into `server.js` with Tailwind left out, the page prebuilt by `buildPage`, the keeper bundled into `keeper.js`, and the starter kit's `agent/`, `config.yml`, and installer bundled into `install.js`.
It bundles the session visuals, Bot, shepherd, designer, and Sport extensions beside them, into `session-visuals-extension.js`, `bot-extension.js`, `shepherd-extension.js`, `designer-extension.js`, and `sport-extension.js`.
It then downloads the Bun of the build's own version for each architecture into `desktop/dist/bun-<arch>`, and runs electron-builder with a config it generates.
That writes a DMG, a zip, their blockmaps, and `latest-mac.yml` to `desktop/release`, or with `--os linux` one AppImage per architecture with `latest-linux.yml` and `latest-linux-arm64.yml`.
It signs and notarizes when `CSC_LINK` and the `APPLE_API_KEY*` variables are set, with the hardened runtime and `desktop/entitlements.mac.plist`, which lets Bun JIT; otherwise it signs ad hoc.
`--mock-update-port <port>` points the update feed at `scripts/mock-update-server.ts`, which serves `desktop/release`, to try an update without publishing.
`.github/workflows/release.yml` runs on every push to `main`, one run at a time with a newer push cancelling an older run, in four jobs.
`test` runs the checks with a read-only token and no secret.
`build` sets `desktop/package.json`'s patch version to the run number, keeping its major and minor, and builds arm64 and x64 on an Apple silicon runner; the signing secrets reach only its signing step, and its token only reads.
`build-linux` sets the same version and builds the x64 and arm64 AppImages, unsigned, with a read-only token.
`publish`, the one job whose token can write, downloads the artifacts and creates a GitHub Release tagged `vX.Y.Z` with every one, running no code from the checkout.
Every action is pinned to a commit, with its tag in a comment, and no checkout keeps its token in `.git/config`.
