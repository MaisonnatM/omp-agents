# Page: status bar, terminal, HTTP reads, shortcuts, and theme

- `web/components/status-bar.tsx`: the window's bottom strip, with `PlanUsageList` from `web/components/plan-usage.tsx` on the left, and on the right the **Terminal** button and the machine's CPU, available memory, and free disk space from `GET /api/system`.
  The CPU fact is a popover, opened by hover or click through `useHoverPopover`, that lists every live session's processes, busiest session first, each session named by `hostLabel` over the roster `app.tsx` passes, and each row with its own `useAction` for **Stop**, which `writeProcessStop` sends; the disk fact's tooltip breaks down the volume that holds the home directory.
- `web/components/terminal/terminal-panel.tsx`: the terminal panel under the panes, its tabs, height, and open state, and `useTerminalPanel`, which saves the last two in localStorage.
  `terminal-tab.ts` holds the tab shape and its lifecycle, `TerminalTabState`, `starting`, `connected`, `closing`, or `disconnected`, which `nextTabState` moves through the socket's `opened` and close and the user's close; closing a starting or connected tab asks its shell to exit through the view and keeps the tab until its socket closes.
  `terminal-inventory.ts` holds `readTerminalTabs`, which turns `GET /api/terminals` into the panel's loading, failed, or ready tabs: a tab per running shell, or one new shell only when the read succeeds and lists none.
  `terminal-view.tsx` draws one tab with xterm.js over its `/ws/terminal` socket, fits it to the panel, follows the page's theme, and passes the toggle chord, and every Cmd chord on macOS, to the page's shortcuts; the panel loads it with `React.lazy`, so xterm.js is a chunk of its own that loads when the panel first opens.
  `terminal-socket.ts` sends its commands and retains a kill requested while the socket connects, sending it when the socket opens.
- `web/quick-actions.ts`: the quick actions of the Pull requests page, the tickets page, and the open todo, which pull requests, issues, and todos each applies to, and the start, with its prompt, that runs it; the pull request actions themselves come from `src/pull-request-actions.ts`.
  Tickets and todos share the **Work on it** and **Plan it** labels and descriptions in `WORK_ACTIONS`, and each keeps its own rules, which of its items an action applies to and the prompt it sends.
  `startTarget` turns what a quick start works on into the `subject` or `todoId` its `start` message carries, and `reviewDraft`, true for **Review** alone, and `quickOn` picks the quick start that works on an item, whose failure that item's details show.
  `web/components/quick-actions.tsx` holds the tickets' row menu, the buttons on a pull request's, an issue's, or a todo's details, and the note that says why a start failed.
  `web/components/session-chip.tsx` holds the chip that names a session on a row or in the details, with the status dot of a running one.
  `web/components/status-dot.tsx` draws that dot for each session status.
- `web/activity.ts`: the activity recorder, its outbox, `VIEWS` and `viewOf`, `commandKey`, `recordAction`, `activityControl`, and `controlOf` with the one click listener for tagged controls; see [Activity](../architecture/activity.md).
  `web/activity-report.ts` builds Settings › Activity's inventory from the page's registries and splits it by use.
- `web/api.ts`: the page's HTTP client, which sends the token from localStorage as `Authorization: Bearer` and marks the page signed out on a 401, `openSocket`, which opens the dashboard's or a terminal's WebSocket with the token as its subprotocol, `wss:` when the page is on HTTPS, and `mediaSrc`, which adds the media key to an `/api/` address that an image, a video, or a frame loads.
  Error responses are narrowed from unknown JSON and retain HTTP context when their body is malformed.
  The page and server share `errorText` from `src/json.ts`.
  `settingsUrl` names a settings route for one workspace, or for the user's own files, and `releaseWorktree` asks the server to remove the linked worktree that has a branch checked out.
  `web/components/signed-in.tsx` holds `SignedIn`, which `web/main.tsx` wraps the app in, so a page without a token says to open the omp agents app, and asks the desktop shell to sign its window in again.
- `web/reads.ts`: the server reads that components hold.
  `useRead` reads one URL, such as a pull request's stack, the settings page's model catalog, or the new-session draft's model list.
  A version change retains the last answer and exposes `refreshing` until the new read settles, including a failed read.
  A URL change never returns the previous URL's answer.
  The polled stores, made by `web/polled-store.ts`, are shared by a sidebar list and its page, kept in localStorage, and re-read every minute while the page is open: one for the pull requests, with one entry per workspace, one for the tickets, with one entry, since Linear is not per workspace, one for the MCP integrations, one for the Google calendars shown, one for the Calendar page's Google events, with one entry per month, one for its events kept on this computer, with one entry, and one for the Gmail inbox, with one entry.
  A tick while the page is hidden reads nothing, and each scope that skipped one reads once when the page shows again.
  Each kept store reads its localStorage back through its `cache.decode` and drops a read the decoder refuses, so a record kept by an older version, or damaged, reads the server again instead of reaching a component.
  `mcpServersStore`, for Settings › MCP servers, and `providersStore` are polled stores kept in memory only.
  So is `sessionProcessesStore`, one entry holding every live session's processes, which the open CPU card polls, and a Preview while it has no address yet or shows its server menu, every 5 seconds rather than every minute.
  `terminalSessionsStore` holds omp's global `collab.autoStart` in memory and polls every five seconds while the Get started dialog is open; `starterKitStore` and `sourceControlStore`, GitHub's and Graphite's CLIs with the workspaces' repositories, poll every minute only there.
  Get started also polls `providersStore` while its dialog or bubble is due, adds focus and explicit refreshes, reuses `integrationsStore`, and `setTerminalAccess` sends the terminal step's `{ access }` write.
  `useGoogleCalendars(workspace)` there tells whether any Google Calendar account is connected and gives the accounts and calendars the workspace shows, for the Calendar tab's sidebar, the Calendar page, and the new-event dialog, and `useEmail(workspace)` the Gmail accounts the workspace shows, their conversations, read through `gmailStore` while any Gmail account is connected, and the account picked in the Email tab, `null` while fewer than two accounts show (`pickedAccount` in `web/email-model.ts`), for the Email page, which alone narrows the list to it, and its tab, which counts each mailbox's unread from the same conversations.
  A read in flight belongs to its entry: a new read of an entry replaces only the read of that entry in flight, and the components that poll one entry share one timer, which starts with the first and stops with the last.
  Its `update` applies a saved change to the current answer and aborts older reads before they can replace that answer.
  `writePullRequest` there sends every `PullRequestChange`, from a pull request's row or its details: it sends `PUT /api/pull-request`, shows a state change or a review request in the workspace's pull request list at once through `withPullRequestState` or `withPullRequestReviewers`, and reads the list again.
  `writeViewedFile` beside it sends the **Code** tab's **Viewed** checkbox to `PUT /api/pull-request/viewed`, which no list shows, so it reads nothing again.
  `writeMergeQueue` is the one write of a merge, from every merge button: it sends `PUT /api/merge-queue` and, for each pull request the server merged on the way, shows it merged in the list at once and reads the list again; `web/use-workspace-scope.ts` reads the list again when a pull request leaves the queue later.
  The details read the pull request again when its state in the list changes, so a change from its row shows in its open details too.
  The Email page's conversations are not a polled store: `readMailThread` and `useMailThread` keep them in memory by thread id, one read each, and a later read supersedes one in flight.
  `web/app.tsx` polls the pull requests instead, on every page once the sessions are listed, for the Pull requests tab's count, and the sidebar's pull request list reads that entry.
  The composer's `@` menu reads the pull request entry that `pullRequestsScope` in the status context names, the one `web/app.tsx` polls, so it starts no poll of its own and never reads the all-workspaces entry, which asks GitHub about every repository, in place of the selected workspace's.
  `web/components/tickets/ticket-pickers.tsx` holds the controlled status, priority, assignee, labels, and project pickers that the issue detail and the new-issue dialog share.
  `web/components/tickets/ticket-fields.tsx` lays those pickers out in the issue detail and sends their changes through the issue's `useEditableRead`; the picker button and its searchable list, and the due date's, live in `web/components/field-picker.tsx`, which the Todo page and a pull request's details share, with an open state its owner can hold so a key opens it, and digits that pick a choice.
- `web/editable-read.ts`: `useEditableRead`, a read that writes change in place, which owns what it shows: the server's last answer, from a read or a write, and the edits not yet answered, shown over it in order.
  Writes go one at a time, and each answer carries how many writes had answered when it was asked, so an older answer never replaces a newer one, and the edits still pending show over each answer that arrives.
  A refused edit is undone, and the page names why.
  A pull request's details, a Linear issue's details and its fields, the settings page's omp settings, and the source control section read through it; the settings editors' saves go through its `write`.
- `web/use-git-checkout.ts`: reads a directory's git checkout for the new-session draft's branch picker.
  `web/components/git.tsx` holds the branch picker, the repository and branch in a header's meta line, and `BranchName`, the branch that copies itself on click, which the pull requests, the tickets, and a session's header also show, and its `onCopy` runs once a click has copied.
  Its `releaseBranch` sends `releaseWorktree` and toasts the worktree it removed or kept, or the failure; the branch a pull request's details bring and a session header's branch call it after a copy.
  `web/use-copy.ts` copies text to the clipboard, resolving once the copy lands, and holds the copied state behind a button's check mark.
  `web/use-draft-model.ts` holds `useDraftModelSelection`, the model and effort of the new-session draft and the replay dialog: the model a start sends, `null` for omp's default, the model the picker shows, which until a pick is the one the `default` role names, and an effort kept only for the model it was picked on; it also reads the model list again whenever the menu opens.
  `web/use-skills.ts` reads a directory's skills, and `web/pinned-skill.ts` keeps the skill pinned for new sessions.
  `web/composer-drafts.ts` keeps each composer's unsent text in localStorage under one key, through `expiringStrings` in `web/expiring-strings.ts`, which also keeps each session's Preview address: `useComposerDraft` for each live session's and subagent's composer (`liveDraftKey`), each Bot's composer (`botDraftKey`), and the new-session draft (`newDraftKey`, one per todo), and `putDraft` and `clearDraft`, through which `web/use-dashboard.ts` puts a fork's prompt in its composer and forgets a started session's first message; `appendToComposer` adds text after a draft, through its composer when one is mounted, as the Browser's picks do; drafts unchanged for 30 days go on the next write.
  Its `attachToComposer` hands a mounted live composer a file, which `useComposerFiles` adds to its attachments, as the Browser's captures do.
  `web/components/skill-picker.tsx` is the skill picker of the settings' pinned skill.
  `web/components/command-picker.tsx` holds `CommandPicker`, the searchable grouped list behind the branch, workspace, and skill pickers, with `CommandResults`, which the model menu's search shares.
  The checkout, the default model's role, and the skills are each one `useRead`.
- `web/shortcuts.ts`: the keyboard shortcut table, which both the key listeners and the shortcut dialog read.
  One `keydown` listener on the window serves every `useShortcuts` registration, which `createShortcutStack` orders: the registration that mounted last tries a key first, and the first handler that takes it ends the press, so a page's own bindings come before `web/use-page-shortcuts.ts`'s, which `web/app.tsx` mounts first, and a handler that returns `false` lets the key fall to the one below.
  A handler gets which of its shortcut's keys was pressed, so the focused pane's `UserRequestCard` binds the one `answer` shortcut, 1 to 9, to its question's options.
  Shortcuts with a `command` title are also the command palette's commands, and `web/app.tsx` hands the palette the same handlers it registers.
- `web/command-palette.ts`: the command palette's model, which renders nothing: its items and their actions, the reducer over its stack of views and its action panel, and the ranking, which multiplies cmdk's match score by a frecency boost kept in localStorage.
  `SECTIONS` there says how each section lists: always, only for a search or under Suggestions with every word required, as the todos, tickets, and pull requests do, in the server's order after those, as the conversation matches do, or after every match, as what the search becomes; `web/palette-records.ts` builds the records' and the matches' items, each opening the page that shows it, a todo through the `?open=` of its list's hash.
  `useConversationHits` in `web/reads.ts` asks `GET /api/conversations` through `useRead` once typing pauses for 200 ms; `highlightOnFound` moves the highlight from what the search becomes to the first item when the matches arrive.
  A match opens its session through `web/message-reveal.ts`, a `keyedStore` by view, which the pane's `Transcript` reads to scroll once to the message after the transcript has loaded.
  `web/components/command-palette/` draws it, opened from the sidebar header or with Cmd+K: `command-palette.tsx` the dialog and its list, `action-panel.tsx` the action panel that Cmd+K opens on the highlighted entry, and `palette-footer.tsx` the footer.
  It mounts only while open, so a closed palette builds no list and polls nothing; it asks for the Linear tickets while Linear answers.
  `web/session-actions.ts` lists what can be done to a session, which both a sidebar row's menu and the palette offer; only an omp past session offers **Resume**.
- `web/theme.ts`: the light, dark, or system theme, which `web/main.tsx` applies before the first render and again on each write of its key, from the settings page, another page, or the server, and `useDarkClass`, whether the `.dark` class stands now.
- `web/scroll-fade.ts`: sets the `.scroll-fade` edge opacities from JS in browsers without scroll-driven animations, such as Firefox, which `web/main.tsx` starts before the first render; elsewhere `web/globals.css` drives them with scroll timelines.
- `web/stored-state.ts`: `useStoredState`, a value kept in localStorage that removes its default rather than store it, which holds the theme, the sidebars, the sidebar's tab layout, the session details tab, the sidebar's workspace, the pinned skill, the pull request list's order, and how often and how lately each command palette entry ran; and `useStoredKeys`, a set of keys on top of it, which holds the sessions pinned in the sidebar and the Pull requests and tickets pages' folded sections.
  It keeps one stored string per key in a `keyedStore`, which each component decodes, so every component that holds the same key sees a change at once, and the Pull requests page and its sidebar index share their folds and order.
  A `storage` event carries a change made in another page of the same origin to the same store, and `onStoredChange` calls a listener after each write of a key.
  A changed key from `PORTABLE_PREFERENCES` also goes to the server through the sender `web/use-dashboard.ts` registers with `sendPreferencesThrough`; `storedPreferences` reads them to seed a server that holds none, and `adoptPreferences` takes the server's without sending them back; see [Preferences](../architecture/preferences.md).
  The page state owns the split ratios rather than a component, so `web/use-dashboard.ts` reads and stores them through the same file's `storedNumber` and `storeOrRemove`.
  `sidebarSessions` in `web/sessions.ts` splits the sessions into the sidebar's pinned, running, interrupted, and past lists, which the page also walks for the previous and next session keys.
  `waitsOnYou` there tells a live session that waits on you, for the waiting count.
  `discoverableSessions` leaves sessions under `/tmp` out of those lists and the workspace picker, and `workspaceSwitch` keeps a started session's workspace only when that directory is discoverable.
