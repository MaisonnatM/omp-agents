# Server: routines, scheduled sends, usage, settings, and tests

- `src/routines.ts`: the routine types and the rules of routines: `nextRunAt`, `nextDueAt`, `isDue`, `isTriggeredBy`, `watchedKinds`, `applyRoutine`, which applies an edit, `isSameSpec`, whether a routine already holds a spec, `parseRoutineSpec`, which checks a `RoutineSpec` for `routines.json` and the socket alike, `parseBotRoutineRequest`, which reads what a Bot's routine tools leave in `routine-inbox/`, the trigger kinds, and a command's length, time, and output limits; see [Routines](../architecture/routines.md).
  `src/server/routines-file.ts` keeps them in `routines.json`, and `src/server/routine-runner.ts` claims their runs, on a schedule, **Run now**, or a trigger's `fire`, sends their messages into their Bots' conversations, and runs their commands in their Bots' workspaces, posting the output back; `RoutinesFile.migrate` moves routines from before Bots to them.
  `src/full-wake.ts` tells a full wake from a dark wake by what `pmset -g systemstate` prints, and the runner starts nothing and posts nothing in a dark wake.
  `src/server/routine-triggers.ts` turns what the bell's pull request, Slack, and calendar checks fetch, and the Gmail inboxes, into sightings, and its `TriggerWatch` tells which are new; see [Triggers](../architecture/routines.md#triggers).
- `src/shared/bot-id.ts` holds a Bot's id, which a session start names, so the session module does not import the Bot model.
- `src/shared/bots.ts`: the Bot model with its kinds, `BOT_KINDS` and `BOT_KIND_INFO`, `applyBot`, and the parsers for `bots.json`, the socket's `bot` change, and `parseBotInboxRequest`, which reads a `BotInboxRequest` from `bot-inbox/`: the `BotJobRequest` a Bot's `set_job` tool leaves, the `BotCreateRequest` a Bot designer's `create_bot` leaves, or the `BotMessageRequest` a Bot's `message_bot` tool leaves, whose text `parseBotMessageText` checks; it also holds `jobLine`, a job's first sentence, which the gallery, a Bot's page, and the Bot extension's list of the other Bots read; see [Bots](../architecture/bots.md).
  `src/server/bots-file.ts` keeps them in `bots.json`, `src/server/bots.ts` binds each Bot to its session, with its kind's extra extension, sends it messages, and names in `startingRoutine` the routine a new Bot of each kind starts with, and `src/omp/bot-extension.ts` is the omp extension that gives a Bot's session its job, memory, routines, and the other Bots and the `remember`, `set_job`, `save_routine`, `delete_routine`, and `message_bot` tools.
  `src/omp/extension-kit.ts` holds what every omp-agents extension shares: the part of omp's extension API it uses, its flags, and the `remember` tool's Markdown memory, which the Bot extension and `src/omp/personal-extension.ts`, the personal assistant's, both use.
  `src/omp/designer-extension.ts` is the omp extension a Bot designer's session also loads, with its rules and the `create_bot` tool, and `src/shared/bot-designer.ts` holds the name and job the New Bot form fills for one, `DESIGNER_NAME` and `DESIGNER_JOB`; see [Bot designers](../architecture/bots.md#bot-designers).
- `src/shared/scheduled.ts`: the scheduled send shapes, among them a continue after a usage limit or a transient fault, `applyScheduled`, which also applies the server's `ContinueChange`s, one continue per session, `parseScheduledSpec`, which checks a `ScheduledSpec` for `scheduled.json` and the socket alike, and `resetName`, which names a plan window's reset for the **Send later** menu and a continue alike; see [Scheduled sends](../architecture/scheduled-sends.md).
  `src/server/scheduled-file.ts` keeps them in `scheduled.json`, and `src/server/scheduled-runner.ts` claims and delivers them.
  `src/server/auto-continue.ts` schedules a session's continue when `turnFailureOf` in `src/omp/turn-failure.ts` reads that a provider's usage limit ended its turn, picking the reset with `continueWhen`, or a transient fault did, backing off over the faults in a row, holds the session until the continue goes, and cancels it when the session starts another turn, moves to an edited prompt, or ends.
  `occupiedBy` there tells whether a turn runs or waits on a question, or the continue holds the session, for the cleanup after a merge.
  `web/scheduled-model.ts` lists the times the **Send later** menu offers, and `web/components/scheduled.tsx` holds the menu, the rows above the composer with `useScheduledEdit`, which restores a message to the composer once the server took it off the schedule, and the sidebar's group, whose rows share `RowLine` from `web/components/session-row.tsx`.
  `web/components/scheduled-session.tsx` is the `#scheduled/<id>` page, which edits a scheduled new session in the new-session draft.
- `src/pull-request-actions.ts`: the pull request actions, which pull requests each applies to and its prompt, which the Pull requests page's quick actions and a PR shepherd's fixes use; both rebasing prompts share `CONFLICT_STEPS`, how a session works through each commit a rebase stops at.
- `src/shared/shepherd.ts`: what a PR shepherd's `fix_pull_request` and `queue_merge` tools ask of the server, `ShepherdRequest` and its parser, and a new shepherd's job and starter routine; `src/omp/shepherd-extension.ts` is the omp extension that gives only a shepherd's session those tools; see [Bots](../architecture/bots.md#pr-shepherds).
- `src/pull-request-approval.ts`: `unapprovedChange`, whether a pull request's head has the same stable `git patch-id` as a commit a reviewer approved, which a shepherd's merge needs.
- `src/usage.ts`: runs `omp usage --json`, parses CLI plan windows, and supplements Claude extra usage through `src/omp/usage.ts` in the original billing currency.
  It names a provider as the page shows it (`providerName`).
  `src/console-credits.ts` reads a Firefox or Zen Claude Console session for the API credits row's monthly grant.
  `src/server/usage-poll.ts` (`UsagePoll`) runs it for the dashboard: on the usage tick and a page's open, each followed by the plan notice check, and fresh for a continue, which skips that check.
- `src/system-load.ts`: reads the machine's CPU percent, available memory, and free disk space for `GET /api/system`; `src/shared/system.ts` holds the shape the page shares.
- `src/settings.ts`: builds the settings page's model routing, omp's own settings, file list, and workflows from one load of omp's settings (`loadSessionSettings` and `ompConfigOf` in `src/omp/config.ts`), and checks and saves its edits.
  An edit it refuses throws its `Rejected`, which `src/server/routes.ts` answers with the error's status.
  `saveAgentSetting` refuses an edit whose `expected` is not the user value `config.yml` holds now (`userValue`) before it writes.
  `src/omp/workflows.ts` (`workflowsOf`) joins the skills and commands omp discovered: the skills whose frontmatter, as omp parsed it, names `workflow` in `metadata.tags`, each paired with the command omp names the same; `src/omp/workflows.test.ts` tests the tag, the pairing, and the order.
  `src/omp/agent-settings.ts` reads omp's settings panel for Settings › omp settings from a loaded settings instance (`readAgentSettings`), building the tabs and groups once, finds the setting an id names unless it changes only how omp's terminal draws (`agentSetting`), reads the user value an edit is checked against (`userValue`), and writes one to `config.yml` (`writeAgentSetting`); `src/shared/agent-settings.ts` holds the rows, controls, change, and edit the page shares, and `src/omp/agent-settings.test.ts` tests the tabs, the controls, credentials, the workspace layer, and the user value.
  `src/omp/agents.ts` reads omp's winning agent definitions, package roots, read-only classification, native model selection, and locally available model resolution from the settings instance the page already loaded; `src/omp/agents.test.ts` checks scope precedence, user-only discovery, model layers, disabled agents, and bundled seance.
  `saveAgentSetting` also parses the typed `AgentOverrideEntryEdit` for one override-map `entry`, compares that user's entry, and writes with native `setEntry`; `src/settings.test.ts` checks the selector shape, entry conflicts, and preservation of other user and workspace entries.
- `src/memory.ts`: reads omp memory for Settings › omp memory, what a new session in the workspace gets and its store, and checks and saves its edits, each refused with `Rejected` from `src/settings.ts` and refused as a conflict when the backend changed since the page read it.
  `src/omp/memory.ts` holds its access to omp: the backend a session resolves, the block a new session gets, Local's and Sharpshooter's files, Mnemopi's banks and rows, which it reads and edits through omp's `Mnemopi`, Hindsight's rows, and the removal of Mnemopi's own banks; `src/shared/omp-memory.ts` holds the shapes the page shares, and `src/memory.test.ts` tests the read, the file save, the clear, the row edits, and the parsers.
- `src/frontmatter.ts`: parses the YAML frontmatter a Markdown file opens with, for decision records (`parseFrontmatter`) and for the page's file views (`frontmatterOf`); `src/frontmatter.test.ts` tests the values as text and the blocks that give none.
- `src/decisions.ts`: reads a repository's decision records for Settings › Decisions; `src/decisions.test.ts` tests a record with and without frontmatter, the directory it picks from a nested directory, and a repository with none.
- `src/extensions.ts`: validates extension changes, queues native mutations, binds script approvals to an operation/workspace, and allowlists contribution previews.
  `src/extensions.test.ts` covers native local marketplace lifecycle, scope and packaged workflow ownership, malformed registry protection, script approval, shared config writes, discovery binding ordering, and invalid-settings fallback.
- `src/test-env.ts`: points `PI_CODING_AGENT_DIR` at a temporary directory, and `CLAUDE_CONFIG_DIR` and `CODEX_HOME` at directories inside it that do not exist, and clears `PI_SESSION_ID`, so the session-trailer hook adds no `Omp-Session` trailer to a test's commits when the tests run from an omp session.
  `bunfig.toml` preloads it for tests, so they never touch `~/.omp/agent`, `~/.claude`, or `~/.codex`.
- `.env.test`: `bun test` loads it before any test, so every child a test starts, even through Bun's default spawn environment, runs git without the developer's global and system config, with a test identity and no auto-maintenance.
  A test's commit never signs through the developer's gpg-agent, which stalls past Bun's 5-second test timeout or fails while other sessions sign; `src/git.test.ts` checks it.
- `.githooks/pre-push`: refuses a push to `main` that leaves `CHANGELOG.md` unchanged, then runs the checks `.github/workflows/checks.yml` runs; the `prepare` script points `core.hooksPath` at `.githooks/` on `bun install`.
- `.githooks/pre-merge-commit`: refuses a merge commit on `main` that leaves `CHANGELOG.md` unchanged, so a branch gets its lines before the merge rather than at the push; `src/githooks.test.ts` tests it.
- `.githooks/post-merge`: warns after a fast-forward into `main` that leaves `CHANGELOG.md` unchanged, which pre-merge-commit never sees; `src/githooks.test.ts` tests it.
