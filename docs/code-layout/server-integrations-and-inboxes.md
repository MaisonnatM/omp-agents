# Server: Linear, Google, todos, shared lists, and inboxes

- `src/tickets.ts`: the Linear side of the tickets page: the `list_issues` queries, their paging, and parsing the issues out of the tool's text, one issue in full for the main content, the options of its field pickers, and the `save_issue` call they make.
  `src/linear-uploads.ts` keeps the signed addresses of an issue's files and serves them.
  `src/mcp-clients.ts` plans a Slack, Google Calendar, or Gmail OAuth client save, the setup each form shows and the server entry the save writes, from omp's MCP servers that `src/omp/mcp.ts` reads and writes; `clientSetup(id)` reads the setup the service's `client` in `MCP_SERVICES` decides.
  `src/integrations.ts` finds omp's servers for each MCP integration, checks them, and runs the sign-ins, removals, and client saves that Settings › Integrations starts, picking each service's kind once from `MCP_SERVICES` in `src/shared/accounts.ts`, a single server or the accounts `src/google-accounts.ts` keeps; see [Integrations](../architecture/http-api-integrations.md).
  Its `integrationFetch(id)` calls Slack's own API with omp's sign-in to Slack's server.
  `src/google-accounts.ts` owns Gmail's and Google Calendar's accounts: the state `google-accounts.json` holds and its reducer, each sign-in onto a credential id of its own, the address claim, Remove, workspace links, and `accountClients`, one client per signed-in account; `src/google-accounts.test.ts` runs adds, reconnects, and Remove through `createIntegrations` against the test environment's scratch omp credential store, with a fake browser grant.
  `src/signed-fetch.ts` holds that HTTP call without anything of omp: `signedFetch` over a `Bearer`, `SignedFetch`, `ApiWrite`, and `ApiError`; `mcpBearer` in `src/omp/mcp.ts` supplies omp's token and its refusal.
  `src/mcp-servers.ts` lists every MCP server omp loads with where omp stands with each, and runs the adds, sign-ins, sign-outs, enables, disables, and removals that Settings › MCP servers starts; see [MCP servers](../architecture/http-api-mcp-servers.md).
  `src/mcp-status.ts` has `remoteStatusOf`, the one reading of a remote server's tool list into its status that both files use.
  `src/providers.ts` lists the model providers and runs the sign-ins and sign-outs that Settings › Providers starts, with `src/provider-logins.ts` holding the one sign-in under way, and `src/omp/providers.ts` calling omp for them; `src/shared/providers.ts` holds the shapes the page shares; see [Providers](../architecture/http-api-providers.md).
- `src/google-calendar.ts`: `GoogleCalendarClient`, one account's calendars checked in its Google Calendar list and the events in a span of those the Calendar page shows, read from Google's Calendar API with omp's sign-in to that account's server, and the events it adds to and deletes from the calendars you may write to; `GoogleCalendars` merges every signed-in account's and sends each write to the account it names.
  `src/server/calendars-file.ts` keeps the ids of the calendars unchecked in the Calendar tab's sidebar in `calendars.json` beside the access token, by account, and moves a file it cannot read to `calendars.json.invalid`.
  `src/server/google-accounts-file.ts` keeps `google-accounts.json` beside the access token: each Google account's address by its server's name, which `src/google-accounts.ts` learns after a sign-in or on a read, and the workspaces each address is linked to, which the starter kit's `extensions/google-accounts.ts` reads too.
  `src/server/local-events-file.ts` keeps the events added to **This computer** in `events.json` beside the access token, and moves a file it cannot read to `events.json.invalid`; see [New and local events](../architecture/http-api-google-calendar.md#new-and-local-events).
  It checks each event's `when` with `parseEventWhen` in `src/shared/calendar.ts`, as `PUT /api/calendar/events/new` does.
- `src/gmail.ts`: `GmailClient`, the latest conversations of one account's Gmail inbox and one conversation in full, read from Google's Gmail API with omp's sign-in to that account's server, and the walk of a message's MIME tree; `GmailAccounts` merges every signed-in account's inbox and sends each read and write to the account it names; see [Gmail](../architecture/http-api-gmail.md).
  `src/server/mail-document.ts` serves a message's HTML as a document of its own, under its own policy, for the Email page's frame.
- `src/sign-in.ts`: `createSignIn`, the one-at-a-time sign-in with a five-minute timeout behind `src/integrations.ts` and `src/mcp-servers.ts`, whose `hold` repeats a server's last status while its sign-in waits on the browser; `createServerSignIn`, the one `src/mcp-servers.ts` keeps per server, names no target.
- `src/cache.ts`: keeps answers for a time to live, 30 seconds for the pull request list's and the tickets', so several tabs share one query; `dropWhere` forgets the keys a predicate names, which `src/commands.ts` uses when a session ends.
- `src/user-todos-shared.ts`: the Todo page's types, which the server, the page, and the extension that reads `todos.json` all follow: `UserTodoList`, `UserTodo`, `UserTodoLink`, `UserTodoChange`, and the statuses (`TODO_STATUSES`, `isClosed`), priorities (`TODO_PRIORITIES`, Linear's scale, as tickets use), and assignees (`TODO_ASSIGNEES`: `user` or `agent`).
  `templates/omp/agent/extensions/todos.ts` cannot import them, so it declares the shape it reads by hand.
- `src/user-todos.ts`: the rules of the Todo page's list, `applyUserTodo`, which the server applies to its file and the page to what it shows before the server answers, and `addTodo`, which builds an `add` with every field filled.
  The list is `UserTodoList`: categories, top-level todos, and the archive that `clear-done` fills, latest first.
  **Clear done** sends `clear-done` for the list it shows, and the server's minute tick in `src/server/dashboard.ts` sends one with `before` for every todo closed over `DONE_KEPT_HOURS` ago; the socket and the todo inbox drop a `before` they receive.
  A todo has a title, markdown notes, a status, a priority, an assignee (`null` for none), a close time (`doneAt`), a due day, and when it was added (`createdAt`, `null` for a todo from before that field); a top-level one also has a category or none, todos of its own, which share its category, links (`UserTodoLink`: a session, a pull request, or a Linear issue), and `addedBy`, the session whose agent added it.
  `set-assignee` sets or clears the assignee at either level; it records who should do the todo and starts nothing, and the todo inbox drops an assignee an agent's `add` carries.
  `doneAt` is set exactly while the status is `done` or `canceled`, which `applyUserTodo` and the parser keep true, so the desktop shell, the calendar, and the extension still read an open todo as one with no `doneAt`.
  `set-status` sets the status and, on closing, `doneAt` to its `at`; closing a top-level todo closes its open todos with the same status and time, and reopening one leaves its todos as they are.
  `set-priority` sets the priority, `move` reorders, `restore` puts back what `remove` took at its index for the page's **Undo**, and `unarchive` and `empty-archive` act on the archive.
  Every list keeps its open todos before its closed ones, at both levels: `applyUserTodo` orders the todos after each change through `inStatusOrder`, and loading the file does too.
  `moveTo` in `web/todo-views.ts` refuses a move to a place with no todo of the same status beside it, and the page adds a todo after the last one of the status it is typed in.
  `src/server/user-todos-file.ts` keeps the list in `todos.json` beside the access token.
  `src/user-todos-parse.ts` reads the list and its changes from JSON for the file, the socket, the todo inbox, and the desktop shell: a file from before any of those fields reads with none of them, a todo with no status as `done` when it has a `doneAt` and `todo` otherwise, and a change from a page or an agent is held to the length limits, a `restore` too.
  A `user-todo` socket message carries one change, and every socket hears the list after it as a `user-todos` message on the roster topic, also sent when a socket opens; a change that changes nothing sends the list back to its own socket alone.
  A `start` of kind `new` may name a `todoId`; once omp starts, `src/server/start.ts` links the todo to the new session through `StartEnv.linkTodo`, before it sends the first message, and `src/server/dashboard.ts` applies the changes `startChanges` in `src/user-todos.ts` returns: the link, and `set-status` `in-progress` for a `backlog` or `todo` todo.
- `src/user-notes-shared.ts`, `src/user-notes.ts`, and `src/user-notes-parse.ts` hold the Notes page's model, reducer, and boundary parsers.
  `src/server/user-notes-file.ts` keeps `notes.json` with `ReducerFile`, registered in `src/server/list-registry.ts` under `user-notes`.
  `src/server/note-inbox.ts` drains agent adds and appends from `note-inbox/` through `JsonInboxDir` while its server owns the lock.
  `templates/omp/agent/extensions/notes.ts` registers `user_note`, reads persisted notes and pending adds, and leaves requests without writing `notes.json`.
  See [User notes](../architecture/user-notes.md).
- `src/shared/workspaces.ts`: the Settings › Workspaces list, `WorkspaceList` of added and hidden directories, its `WorkspaceChange`, and `applyWorkspace`, which the server applies to its file.
  `src/server/workspaces-file.ts` keeps the list in `workspaces.json` beside the access token and moves a file it cannot read, or one that holds a relative path, to `workspaces.json.invalid`.
  At startup, before either file loads, the `Dashboard` constructor calls its `adoptOldWorkspaces`, which moves `projects.json`, where an older version kept the list, to `workspaces.json` when it holds a workspace list and `workspaces.json` does not exist; a `projects.json` in any other shape stays where it is.
  The move links the new name, then unlinks the old one, so it never replaces a `workspaces.json` that a server beside it wrote, and any other failure is logged rather than stopping the server.
- `src/shared/pins.ts`: the sidebar's pins, their `PinChange`, and `applyPins`, which the server applies to its file and the page to the pins it shows before the server answers; see [Pins](../architecture/pins.md).
  `src/server/pins-file.ts` keeps them in `pins.json` beside the access token and moves a file it cannot read to `pins.json.invalid`.
- `src/shared/preferences.ts`: `PORTABLE_PREFERENCES`, the localStorage keys that follow the user across machines, their `PreferenceChange`, `parsePagePreferences`, and `applyPreference`, which the server applies to its file; see [Preferences](../architecture/preferences.md).
  `src/server/preferences-file.ts` keeps them in `preferences.json` beside the access token and moves a file it cannot read to `preferences.json.invalid`.
- `src/shared/notices.ts`: the bell's `Notice`, an update (a newer omp, a `ModelUpdate`, or new commits for omp-agents itself) with its `NoticeStatus`, a pull request with your move, a Slack message, a used-up plan window, a provider out of credits, a calendar event, or the dashboard sessions that stopped mid-turn, with its seen and read flags, and the socket's `NOTICE_OPS`.
  `src/server/notices.ts` checks for them and runs the updates through `src/omp/release.ts`, `src/settings.ts`, and `src/server/self-update.ts`; `src/omp/model-updates.ts` finds the newer models and the routing edits that switch to them, `src/slack-messages.ts` the Slack messages that wait on you, and `src/omp/stats.ts` the providers out of credits; see [Notifications](../architecture/notifications.md).
- `src/shared/desktop-bridge.ts`: `DesktopBridge`, what the desktop shell's preload gives the page as `window.ompDesktop`, its IPC channels, among them `ACCESS_CHANNEL`, through which the preload gets the page's `localStorage` entries, `SessionAlert`, one moment a session came to need you, which the page raises and the shell's main process shows, and `NOTIFICATION_SOUNDS`, the sounds it may play.
- `src/shared/moves.ts` holds `moveOf`, `agentOn`, `actionFacts`, `readyOnceChecksPass`, and `YOUR_MOVES`, shared by the Pull requests page and bell, and `yourMoves`, the pull requests whose move is yours, which the bell and the routines' pull request trigger both read.
  Its `PrimaryControl` union and pure `primaryControl` choose the header control, with finished states before conflicts, drafts, an armed merge, and a merge now or when ready.
- `src/server/json-inbox.ts`: `JsonInboxDir<T>`, the directory of one-JSON-file requests that `todo-inbox.ts`, `note-inbox.ts`, `routine-inbox.ts`, and `end-inbox.ts` read.
  Each inbox gives it a `parse` that turns a file into a request, or says why it is not one, and an `apply` that returns whether the file is done.
  A drain reads the files oldest name first, moves a file that does not parse, or whose `apply` throws, to `<name>.invalid` with a logged reason, deletes a file once `apply` returns true, and leaves one that returns false for the next drain.
  A drain lists and reads through `node:fs/promises`, so a burst of requests never blocks the event loop, reads the files it claimed at once, and applies them in name order.
  Overlapping drains never apply a file twice, a drain never rejects, `watch()` creates the directory and drains when it changes, and `stop()` closes the watcher.
  An inbox may take an `active` check; while it is false every file stays untouched, invalid ones included.
- `src/server/routine-inbox.ts`: `RoutineInbox`, which applies the `BotRoutineRequest`s a Bot's `save_routine` and `delete_routine` tools (`src/omp/bot-extension.ts`) leave in `routine-inbox/` beside `routines.json`, through the list registry, and drains only on the server that owns the lock.
  It checks each request against the routines as it applies, so a Bot saves or deletes only its own routines, and moves any other request, or one the routines refuse, to `<name>.invalid` with a logged reason; see [Routines](../architecture/routines.md).
- `templates/omp/agent/extensions/github/owner-lock.ts`: `OwnerLock`, the `server.lock` that picks the server that runs unattended work, per-file ownership for shared reducer writes, task-launch claims, and coordinated GitHub access; see [One server runs the unattended work](../architecture/routines.md#one-server-runs-the-unattended-work).
- `src/server/todo-inbox.ts`: applies the changes that omp's `user_todo` tool (`templates/omp/agent/extensions/todos.ts`) leaves in `todo-inbox/` beside `todos.json`, one JSON file each, written under a `.tmp` name then renamed, and drains only on the server that owns the lock.
  `parseAgentChange` reads each file in the extension's own format: an `add` becomes a `todo` of no priority added at that time, a `toggle` that checks becomes `set-status` `done` at its time, and an `edit`, `edit-body`, `set-due`, `categorize`, or `remove` reads as the page's own change.
  The inbox takes those changes, deletes each file it applies, and moves any other, such as an uncheck, another status, a move, or a change to the categories, to `<name>.invalid` with a logged reason, so the server stays the only writer of `todos.json`.
  The extension's `before_agent_start` handler reads `todos.json` at each prompt and adds to the system prompt the title and id of the open top-level todo that links to its session, and of each other open one whose `addedBy` is its session, so the agent checks them off once done.
  `add` returns the open todo its session already added with the same title instead of adding it again.
- `src/server/end-inbox.ts`: ends the sessions that omp's `end_session` tool (`templates/omp/agent/extensions/end-session.ts`) asks to end, one `<session id>.json` each in `end-inbox/` beside `todos.json`.
  The tool writes its request at `agent_end`, after the turn that called it, and deletes it at the next `agent_start` or `session_shutdown`, so a request names a session that idles.
  The inbox drains when the directory changes and after each registry poll, finds the live session through `LiveSessions.bySessionId`, ends it through the **End session** path with its checkout retention and removal checks, then deletes the request.
  A request is `{ v: 1, sessionId }`; `END_REQUEST_VERSION` is the version this server reads, a request without `v` reads as version 1, and one of any other version moves to `<name>.invalid`, so a later change to the request's shape has a version to key on.
  A request whose session this server does not host yet stays for a later drain, and so does one for a session started in a terminal while another server owns the lock, since every server follows those; a file that is not a request, or whose name is not its session id, moves to `<name>.invalid`.
- `src/tickets.ts` also lists the workspace's Linear teams with their keys (`loadTeams`, `GET /api/linear/teams`) and its active members for the composer's People (`loadLinearUsers`, `GET /api/linear/users`), and opens an issue (`createTicket`, `PUT /api/ticket/new`), assigned to the viewer unless the draft names another assignee or `null`, with any fields the draft sets, from the new-issue dialog (`web/components/tickets/new-ticket.tsx`), which `App` opens through `openNewTicket` in the dashboard context.
  The dialog's pills are the issue's pickers from `web/components/tickets/ticket-pickers.tsx` and the shared `DuePicker` with `look="chip"`, and `web/components/tickets/team-select.tsx` remembers the last team used, for the dialog and the todo's team select alike.
  `attachToTicket` (`PUT /api/ticket/attachment`) attaches a file in base64 to an existing issue: Linear's `prepare_attachment_upload` signs a storage URL, the server sends the bytes there with the signed headers, then `create_attachment_from_upload` links the file to the issue.
  `src/server/todo-ticket.ts` holds `createTicketForTodo` (`PUT /api/todo/ticket`), which opens an issue from a top-level todo and links it, answering only once the server's todo list holds the link, or with the identifier and why it does not; it refuses a todo that already links an issue before opening one.
