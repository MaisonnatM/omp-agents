# Server: integrations, shared lists, and inboxes

- `src/mcp-clients.ts`: plans a Slack OAuth client save, the setup its form shows and the server entry the save writes, from omp's MCP servers that `src/omp/mcp.ts` reads and writes; `clientSetup(id)` reads the setup the service's `client` in `MCP_SERVICES` decides.
  `src/integrations.ts` finds omp's server for each MCP integration, the first on its host in `MCP_SERVICES` in `src/shared/accounts.ts`, checks it, and runs the sign-ins, removals, and client saves that Settings › Integrations starts; see [Integrations](../architecture/http-api-integrations.md).
  Its `integrationFetch(id)` calls Slack's own API with omp's sign-in to Slack's server.
  `src/signed-fetch.ts` holds that HTTP call without anything of omp: `signedFetch` over a `Bearer`, `SignedFetch`, `ApiWrite`, and `ApiError`; `mcpBearer` in `src/omp/mcp.ts` supplies omp's token and its refusal.
  `src/mcp-servers.ts` lists every MCP server omp loads with where omp stands with each, and runs the adds, sign-ins, sign-outs, enables, disables, and removals that Settings › MCP servers starts; see [MCP servers](../architecture/http-api-mcp-servers.md).
  `src/mcp-status.ts` has `remoteStatusOf`, the one reading of a remote server's tool list into its status that both files use.
  `src/providers.ts` lists the model providers and runs the sign-ins, sign-outs, and account orders that Settings › Providers starts, with `src/provider-logins.ts` holding the one sign-in under way, and `src/omp/providers.ts` calling omp for them.
  `src/omp/providers.test.ts` checks that a new Anthropic API key replaces older keys and leaves subscription sign-ins in place.
  `src/omp/account-order.ts` ranks a provider's accounts by the priorities of omp's `auth.accountPolicies` and writes a new order back into that setting; `src/omp/account-order.test.ts` checks the ranking, that a new order keeps other entries and fields, and the write into `config.yml`.
  `src/omp/api-credits.ts` writes the API credits provider into `models.yml` and moves a key that was stored beside the Anthropic sign-in. The server calls that move once as it starts.
  `src/shared/providers.ts` holds the shapes the page shares.
  See [Providers](../architecture/http-api-providers.md).
- `src/linear.ts`: `readLinearIssue`, the issue `GET /api/linear/issue` answers, read with `callMcpTool` from `src/omp/mcp.ts` on the first server omp loads on `mcp.linear.app` and kept 30 seconds by `createCache` from `src/cache.ts`; `parseLinearIssue` turns `get_issue`'s answer into a `LinearIssue` from `src/shared/linear.ts`, with Linear's mention tags outside code made into Markdown links, and `NoLinearServer` is the error when omp loads no such server.
- `src/sign-in.ts`: `createSignIn`, the one-at-a-time sign-in with a five-minute timeout that `src/integrations.ts` keeps per service and `src/mcp-servers.ts` per server, whose `hold` repeats a server's last status while its sign-in waits on the browser.
- `src/cache.ts`: keeps answers for a time to live, 30 seconds for the pull request list's, so several tabs share one query; `dropWhere` forgets the keys a predicate names, which `src/commands.ts` uses when a session ends.
- `src/shared/sport.ts`, `src/sport.ts`, and `src/sport-parse.ts` hold the Sport module's state, its reducer `applySport`, and its boundary parsers.
  `src/sport-week.ts` derives the week, each exercise's load, the pain flags, the best grades, the records, and the adherence from the state.
  `src/server/sport-file.ts` keeps `sport.json` with `ReducerFile`, which `SPORT_MODULE` in `src/sport-module.ts` opens as the Sport module's store; see [Modules](../architecture/modules.md).
  `src/sport-agent.ts` holds `agentSportChanges`, which turns a `sport` tool request into the changes an agent may make, and `withAgentChanges`, the state with the requests an inbox still holds.
  `src/server/sport-inbox.ts` drains the `sport` tool's requests from `sport-inbox/` through `JsonInboxDir` while its server owns the lock, and deletes a file only once the dashboard has written its changes to `sport.json`.
  `src/omp/sport-extension.ts`, which every dashboard session loads, registers `sport`, reads the state with pending requests, and leaves one request per call without writing `sport.json`.
  `src/server/sport-thumbs.ts` serves `GET /api/sport/thumb`, each demo's YouTube thumbnail, fetched once and kept in `sportThumbsDir` from `src/paths.ts`.
  `src/sport-fixtures.ts` holds the sample plan and the builders the Sport tests share.
  See [Sport](../architecture/sport.md).
- `src/shared/projects.ts` holds the Projects module's state, `ProjectList`, its changes, their parsers, and its reducer `applyProjectChange`, which the server applies to its file and the page to what it shows before the server answers.
  `src/server/projects-file.ts` keeps `project-list.json` with `ReducerFile`, and `src/server/projects-inbox.ts` drains `project-inbox/`, the changes the starter kit's `project` extension leaves, any change the page makes; `PROJECTS_MODULE` in `src/projects-module.ts` opens both.
  `src/server/project-migration.ts` holds `migrateBoardProjects`, which the store's open runs to move the projects of an old `board.json` into the list once and rename the file `board.json.removed`.
  A `start` of kind `new` may name a `projectId`; once omp starts, `src/server/start.ts` puts the new session in that project through `StartEnv.joinProject`.
  See [Projects](../architecture/projects.md).
- `templates/omp/agent/extensions/board/log.ts` holds the Board's events, their parser, and the fold the server, the page, and the `board` tool share, tested in `src/server/board-log.test.ts`.
  `src/server/board-log.ts` keeps `board-events.jsonl` as an append-only log, and `BOARD_MODULE` in `src/board-module.ts` opens it with the inbox that drains `board-changes/`, the changes the starter kit's `board` extension leaves.
  `src/server/board-runner.ts` holds `BoardRunner`, which starts a session on each ready Board task, wakes the session a reply is for, and sweeps lapsed leases, through the `ModuleRunCore` that `src/server/unattended-work.ts` gives it, tested in `board-runner.test.ts`.
  See [Board](../architecture/board.md).
- `src/shared/memory-page.ts` holds the Memory module's shapes, which the page shares: project memory, its edit, the bookmarks, and the X sync's state.
  `MEMORY_MODULE` in `src/memory-module.ts` serves its routes, `GET` and `PUT /api/project-memory`, `GET /api/bookmarks`, `POST /api/bookmarks/x-sync`, and `GET /api/bookmarks/x-video`, and joins every session with the `bookmarks` tool; see [Modules](../architecture/modules.md).
  `src/project-memory.ts` reads each workspace repository's `refs/omp/memory` and applies the page's edits as source `#dashboard`, with the `project_memory` tool's code in `templates/omp/agent/extensions/project-memory/`, tested in `src/project-memory.test.ts` against temp repositories.
  `src/bookmarks/` holds the bookmarks: `zen.ts` reads Zen's bookmarks and x.com sign-in from copies of its profile's `places.sqlite` and `cookies.sqlite`, `x-sync.ts` reads the x.com bookmarks and their media through X's own `Bookmarks` query, `x-video.ts` relays a post's video to the page, `translate.ts` puts the posts in another language into English through Google Translate, `store.ts` keeps the last sync in `bookmarks-x.json` in the data directory and merges both sources, `search.ts` searches them for the tool, and `service.ts` holds `Bookmarks`, which serves the routes and runs the sync.
  Each has its test beside it, against temp databases and a trimmed X answer from `fixtures.ts`.
  `src/omp/bookmarks-extension.ts`, which every dashboard session loads, registers `bookmarks`, which searches Zen's bookmarks and the last X sync's posts.
  See [Memory page](../architecture/memory-page.md).
- `templates/omp/agent/extensions/inbox/client.ts`: what every tool that leaves changes in an inbox shares, the starter kit's `board` and `project` tools and the `sport` tool under `src/omp/` alike: `CONFIG_DIR`, `readJson`, the tool `reply`, and `inbox<T>(dir)`, whose `leave` writes one change under a `.tmp` name then renames it, under a name that sorts after the one before it, and whose `waiting` reads the changes the dashboard has not applied yet, oldest first.
- `src/shared/workspaces.ts`: the Settings › Workspaces list, `WorkspaceList` of added and hidden directories, its `WorkspaceChange`, and `applyWorkspace`, which the server applies to its file.
  `src/server/workspaces-file.ts` keeps the list in `workspaces.json` beside the access token, drops the `personal` list an older version wrote, and moves a file it cannot read, or one that holds a relative path, to `workspaces.json.invalid`.
  At startup, before either file loads, the `Dashboard` constructor calls its `adoptOldWorkspaces`, which moves `projects.json`, where an older version kept the list, to `workspaces.json` when it holds a workspace list and `workspaces.json` does not exist; a `projects.json` in any other shape stays where it is.
  The move links the new name, then unlinks the old one, so it never replaces a `workspaces.json` that a server beside it wrote, and any other failure is logged rather than stopping the server.
- `src/shared/project-trust.ts`: a project's agent code, `PROJECT_CODE_KINDS` in the order the census sorts them, `ProjectCode` with its kind, opaque id, display name, and hash, the `TrustAsk` a refused start carries, `TrustedProject`, its `TrustChange`, and `applyTrust`.
  `src/server/project-code.ts` holds `projectCensus`, which names and hashes the files and MCP servers `discoverProjectCode` in `src/omp/discovery.ts` finds.
  `src/server/project-trust-file.ts` keeps the trusted hashes in a shared `project-trust.json`, registered in `src/server/list-registry.ts` under `project-trust`; its `untrustedCode` checks a directory's census against them, and its `admit` throws an `UntrustedProjectError` with the ask, whose message is `untrustedText`, the refusal an unattended start or a move gets; see [Project trust](../architecture/project-trust.md).
- `src/shared/pins.ts`: the sidebar's pins, their `PinChange`, and `applyPins`, which the server applies to its file and the page to the pins it shows before the server answers; see [Pins](../architecture/pins.md).
  `src/server/pins-file.ts` keeps them in `pins.json` beside the access token and moves a file it cannot read to `pins.json.invalid`.
- `src/shared/modules-off.ts`: `MODULES_OFF_KEY`, the portable preference that lists the modules turned off, and `parseModulesOff`, which the page and the server read it with, dropping unknown ids.
- `src/shared/preferences.ts`: `PORTABLE_PREFERENCES`, the localStorage keys that follow the user across machines, their `PreferenceChange`, `parsePagePreferences`, and `applyPreference`, which the server applies to its file; see [Preferences](../architecture/preferences.md).
  `src/server/preferences-file.ts` keeps them in `preferences.json` beside the access token and moves a file it cannot read to `preferences.json.invalid`.
- `src/shared/notices.ts`: the bell's `Notice`, an update (a newer omp, a `ModelUpdate`, or new commits for omp-agents itself) with its `NoticeStatus`, a pull request with your move, a Slack message, a used-up plan window, a provider out of credits, or the dashboard sessions that stopped mid-turn, with its seen and read flags, and the socket's `NOTICE_OPS`.
  `src/server/notices.ts` checks for them and runs the updates through `src/omp/release.ts`, `src/settings.ts`, and `src/server/self-update.ts`; `src/omp/model-updates.ts` finds the newer models and the routing edits that switch to them, `src/slack-messages.ts` the Slack messages that wait on you, and `src/omp/stats.ts` the providers out of credits; see [Notifications](../architecture/notifications.md).
- `src/shared/desktop-bridge.ts`: `DesktopBridge`, what the desktop shell's preload gives the page as `window.ompDesktop`, its IPC channels, among them `ACCESS_CHANNEL`, through which the preload gets the page's `localStorage` entries, `PICK_DIRECTORY_CHANNEL`, behind `pickDirectory`, the native folder dialog Settings › Workspaces opens, and `OPEN_DASHBOARD_CHANNEL`, behind `openDashboard`, which opens another omp-agents server's page in an app of its own, `SessionAlert`, one moment a session came to need you, which the page raises and the shell's main process shows, and `NOTIFICATION_SOUNDS`, the sounds it may play.
  It also holds the checks the Browser's preload and the page run: `isPreviewSelection` and `isPreviewElement` on what the app reports, and `isTypingTarget`, which keeps a key typed in a text field from a shortcut.
- `src/shared/moves.ts` holds `moveOf`, `agentOn`, `actionFacts`, `readyOnceChecksPass`, and `YOUR_MOVES`, shared by the Pull requests page and bell, and `yourMoves`, the pull requests whose move is yours, which the bell and the routines' pull request trigger both read.
  Its `PrimaryControl` union and pure `primaryControl` choose the header control, with finished states before conflicts, drafts, an armed merge, and a merge now or when ready.
- `src/server/json-inbox.ts`: `JsonInboxDir<T>`, the directory of one-JSON-file requests that `sport-inbox.ts` and `end-inbox.ts` read.
  Each inbox gives it a `parse` that turns a file into a request, or says why it is not one, and an `apply` that returns whether the file is done.
  A drain reads the files oldest name first, moves a file that does not parse, or whose `apply` throws, to `<name>.invalid` with a logged reason, deletes a file once `apply` returns true, and leaves one that returns false for the next drain.
  A drain lists and reads through `node:fs/promises`, so a burst of requests never blocks the event loop, reads the files it claimed at once, and applies them one at a time in name order, after the files of a drain already under way, so an async `apply` keeps that order too.
  Overlapping drains never apply a file twice, a drain never rejects, `watch()` creates the directory and drains when it changes, and `stop()` closes the watcher.
  An inbox may take an `active` check; while it is false every file stays untouched, invalid ones included.
- `templates/omp/agent/extensions/github/owner-lock.ts`: `OwnerLock`, the `server.lock` that picks the server that runs unattended work, per-file ownership for shared reducer writes, task-launch claims, and coordinated GitHub access; see [One server runs the unattended work](../architecture/routines.md#one-server-runs-the-unattended-work).
- `src/server/end-inbox.ts`: ends the sessions that omp's `end_session` tool (`templates/omp/agent/extensions/end-session.ts`) asks to end, one `<session id>.json` each in `end-inbox/` beside the access token.
  The tool writes its request at `agent_end`, after the turn that called it, and deletes it at the next `agent_start` or `session_shutdown`, so a request names a session that idles.
  The inbox drains when the directory changes and after each registry poll, finds the live session through `LiveSessions.bySessionId`, ends it through the **End session** path with its checkout retention and removal checks, then deletes the request.
  A request is `{ v: 1, sessionId }`; `END_REQUEST_VERSION` is the version this server reads, a request without `v` reads as version 1, and one of any other version moves to `<name>.invalid`, so a later change to the request's shape has a version to key on.
  A request whose session this server does not host yet stays for a later drain, and so does one for a session started in a terminal while another server owns the lock, since every server follows those; a file that is not a request, or whose name is not its session id, moves to `<name>.invalid`.
